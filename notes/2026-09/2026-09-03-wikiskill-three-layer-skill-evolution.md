# WikiSkill：三层知识架构让 Agent Skill 自我进化

## 1. 这是什么

Google Research + Virginia Tech 于 2026-08-27 发布在 arXiv 的论文（v1 预印本，未经同行评审确认）。
解决的问题：Agent 自动进化 Skill 时，经验散落在历次优化记录里——跑完任务直接改规则，
原始轨迹和失败教训不留存，容易越改越崩。WikiSkill 的答案是在"原始经验"和"可执行技能"
之间加一层持久化的 Wiki 知识库，让技能进化建立在可累积、可检索的知识上。

灵感来源明确：Karpathy 2026 年 4 月提出的 LLM Wiki 方法论（把经验编译成持久、复利的知识，
而不是每次重新检索拼装）。

## 2. 原始来源

- 发现入口：打捞处群内转发的中文解读帖（小红书/公众号风格，末尾带"要不要改成小红书版本"引流钩子）
- 资料本体：https://arxiv.org/abs/2608.27454 （HTML 全文：https://arxiv.org/html/2608.27454v1）
- 深度二手解读（日译英，细节核对价值高）：https://xenospectrum.com/en/google-wikiskill-agent-memory
- 论文附录 E 公开了 Wiki Maintainer 和 Skill Proposer 的完整 system prompt

## 3. 核心观点 / 核心能力

**三层架构：**

- **Raw Layer（raw/，档案馆）**：每次 rollout 的完整轨迹（推理、工具调用、返回、最终答案），
  不可变、不可覆盖。
- **Wiki Layer（wiki/，知识库，核心）**：Wiki Maintainer 从轨迹中复盘提炼 Pattern 页
  （Markdown），记录成功策略、失败根因、每轮技能修改提案、验证得分、是否采纳。
  失败提案也完整留存（`skill-impact.md`），防止后续重复试错。**Wiki 永久累加，技能回滚
  不影响 Wiki。**
- **Skill Layer（skills/，工作手册）**：只放通过验证、正式生效的技能（SKILL.md，含触发条件
  和步骤），执行 Agent 只读这一层。效果变差可直接版本回退。

**四阶段循环：** Inference Agent 跑训练任务 → Wiki Maintainer 把轨迹提炼进 Wiki
（每轮最多选 8 条：≤5 失败 + ≤3 成功，单条截断 15k 字符）→ Skill Proposer 按需检索
Wiki/轨迹，每轮只提一个技能改动 → Gating：在独立验证集上跑分，严格超过历史最佳才采纳，
否则回滚技能（但 Wiki 不回滚）。

**关键实证：**

- 五个基准（数学、网页搜索、表格、长文档 QA、ALFWorld 交互环境）× 五个模型（Qwen 4B/9B/27B、
  Gemma-4-31B、Gemini-3.5-Flash），WikiSkill 全面优于 Trace2Skill / EvoSkill / SkillOpt。
- 技能与模型规模互补：Qwen 家族 4B/9B/27B 的提升分别为 +12.3 / +17.5 / +23.9 个百分点，
  **模型越大越能从技能进化中获益**。
- 小模型+技能可越级：Qwen-3.5-9B + WikiSkill 平均 47.4% > Qwen-3.6-27B 无技能 39.4%。
- **跨模型迁移是亮点而非纯风险**：ALFWorld 上 9B 用 27B 进化出的技能得 70.2%，高于用自己
  进化技能的 63.4%。论文结论：**"技能发现"和"技能执行"是两种不同能力**——暗示贵模型当
  教练造技能、便宜模型执行的分工。
- 消融：持久化 Wiki 是收益关键。一个反直觉发现：**执行 Agent 直接读 Wiki 反而有害**
  （Gemini-3.5-Flash 上：执行端不读 Wiki、只给 Proposer 读 = 63.7%；执行端也开放 Wiki
  访问 = 60.9%，掉 2.8 点）。Wiki 是"技能编辑层"，不是执行时的"答题记忆库"；执行端直接
  抄 Wiki 会让轨迹失去诊断价值。

## 4. 我学到了什么

1. **"证据 → 知识 → 规则"三层分离，且回滚边界不同**：规则可回滚，知识和证据不回滚。
   失败的修改方案本身是资产（`skill-impact.md` 记录提案内容+验证分+采纳决定）。
2. **Gating 是进化不崩的保险**：每次只提一个改动，独立验证集跑分，严格超越才上岗。
   没有评测函数的场景（开放式任务）这套机制无法直接套用——它自动化的是"有标准答案、
   能判分"条件下把经验编辑成流程的过程。
3. **Wiki 不是大而全的上下文填充物**：Maintainer 每轮只摄入 ≤8 条截断轨迹，Proposer 靠
   检索按需读 Pattern 页，而不是把历史全量塞进 prompt。
4. **执行端与编辑端权限分离**：执行 Agent 只读 Skill 层；Wiki 只给复盘/提改动的角色用。

## 5. 它是否可信，哪些需要验证

- 论文为 arXiv v1 预印本，未确认同行评审；数字来自三次独立运行 + bootstrap 显著性检验。
- **最大的未验证点：技能检索/触发完全没测**。实验中是把所有有效技能全文直接注入 system
  prompt，回避了"技能多了之后能不能选对、上下文放不放得下"的问题——作者自己列为待解决。
- 验证集极小（10–40 条/基准），单次 gating 采纳决策有噪声；严格"必须超越"会误杀有长期
  潜力的中性改动。
- Wiki 无自动整理/剪枝机制，长期膨胀；数百步、数小时的长任务未评测；单次执行中途不更新技能。
- 成本：优化侧 LLM 调用约 1 + 10~20 次/轮（不随训练集增长），但生成轨迹的执行成本另算。
- 中文解读帖的两处偏差需注意：①"去掉 Wiki 掉 15 个点"方向对但省略了"执行端读 Wiki 反而
  掉分"这个更关键的细节；②"跨模型迁移必须重新验证、小模型补丁拖累大模型"是合理风险提醒，
  但论文实证主结论其实是**跨模型迁移普遍有效、大模型造的技能给小模型用效果更好**。

## 6. 对个人能力有什么价值

- 给"怎么改 Skill 才不越改越崩"提供了可照搬的纪律：改之前先留证据、一次只改一处、
  改完用固定任务集回归、失败改动也要记档。
- "技能发现 ≠ 技能执行"为已有的工作流提供了论文级佐证：贵模型动脑造方法/写计划，
  便宜模型动手执行——方法论上成立，且教练模型越强，产出的技能越值钱。

## 7. 对企业 AI 落地有什么价值

- 对标 J-Herm/Hermes 体系，三层雏形已存在但有缺口：
  - Raw 层 ≈ session DB + 飞书消息 + 工具日志（有，但结构化轨迹留存不完整）；
  - Wiki 层 ≈ 打捞处 notes + 知识库 + memory（有，但缺"失败提案留档"和 Pattern 化复盘）；
  - Skill 层 ≈ skills/ 目录（有）；
  - **缺口在 Gating**：目前 skill 改动主要靠判断+人工审批（周五成长周报），没有"固定验证
    任务集 + 自动跑分 + 不达标回滚"的机制。
- 直接设计含义：执行对话不应把 Wiki/笔记全量注入上下文（现状一致，靠 skill 触发加载）；
  Wiki 的消费者是"复盘和改技能"的角色，不是答题时的执行 Agent。
- 对 CRM AI 化/带教助手这类没有标准答案的开放任务，WikiSkill 的自动 gating 不能直接套用，
  但"失败经验留档 + 改动小步 + 人审关口"可以人工版实现。

## 8. 可做的小实验

1. 给高频改动的 skill（如飞书相关、gateway 排障类）建一个 `skill-impact` 记录：每次 patch
   记动机、验证方式、结果；回滚的改动也留档。
2. 挑 1-2 个技能建"固定回归小任务集"（10 条以内真实历史 case），改动后跑一遍再上岗，
   人工版 gating。
3. 试点"贵模型造技能"：用主模型（doubao-seed-evolving）复盘某类失败轨迹产出 skill 提案，
   交给便宜模型执行验证，对照自产技能的效果。

## 9. 风险和边界

- 论文环境（仿真基准、有标准答案、技能全文注入）与真实企业部署差距大；技能检索、
  长任务、Wiki 膨胀三大问题均未解。
- 不可把"9B 打赢 27B"误读为小模型够用——前提是技能由强进化流程产出，且大模型自身获益
  更大（+23.9 点）。
- 自动改技能 + 自动上线在无评测函数的业务场景风险高，必须保留人审。

## 9b. 与 Karpathy LLM Wiki 的区别（2026-09-03 追问补充）

两者是"思想源头"和"工程化应用"的关系，WikiSkill 论文明确引用 Karpathy 2026-04 的
LLM Wiki gist 作为 Wiki 层的灵感来源，但应用场景和架构有本质区别：

| 维度 | Karpathy LLM Wiki（2026-04，GitHub Gist） | WikiSkill（2026-09 论文） |
|---|---|---|
| 解决什么 | 个人知识管理：素材喂进来，LLM 编译成互链 markdown wiki，问答时直接查 wiki 而不是每次重新读原文（替代 RAG 的"每次重推导"） | Agent 技能进化：从执行轨迹中复盘，持续改进可执行技能文件 |
| 知识内容 | 关于**世界/领域**的知识（文章、论文、笔记提炼的实体页、主题页、矛盾点） | 关于**Agent 自己怎么干活**的经验（成功策略、失败根因、技能改动提案、验证得分、采纳/回滚记录） |
| 谁消费 Wiki | 人 + 回答问题的 LLM——wiki 本身就是答题时的知识来源，运行时直接读 | **执行 Agent 不读**（消融实测：执行端读 wiki 反而掉 2.8 分）；wiki 只给复盘角色（Maintainer/Proposer）用 |
| 产出物 | wiki 页面即终点（理解和问答） | wiki 是中间层，终点是 Skill 层的可执行规则 |
| 质量机制 | 无 gating：人工 lint、矛盾标注、置信度标记 | 自动 gating：每轮一个改动，独立验证集跑分，严格超越才上岗，否则回滚（wiki 不回滚） |
| 前提条件 | 无，开放域素材即可 | 需要有标准答案/评分函数的任务集（train/val/test 划分） |
| 层级 | 两层：raw 素材 + wiki | 三层：raw 轨迹 + wiki + skills（可回滚的执行层） |

一句话类比：LLM Wiki 是团队的**资料库/图书馆**，员工干活时随时查阅；WikiSkill 是
**训练复盘室**——教练组看比赛录像（raw）、把教训写成复盘笔记（wiki）、只有在训练中
验证有效的改动才印进一线员工随身带的 SOP 手册（skills），员工上现场只带手册、不背整个图书馆。

对我们体系的映射：打捞处 notes + llm-wiki skill 跑的是 Karpathy 模式（知识编译，供理解和
问答）；skills/ 目录 + 周五成长复盘 + memory 是简化版 WikiSkill 模式，但缺 gating（固定
回归任务集 + 跑分 + 回滚）和失败提案留档。

## 10. 当前结论

值得作为 J-Herm 技能进化机制的参照系长期跟踪。三层架构与我们现状同构度高，最值得补的
两块是：**失败改动留档（skill-impact）**和**固定任务集回归 gating**。"执行端不读 Wiki、
贵模型造技能便宜模型执行"两点对现有架构设计有直接指导意义。待官方开源代码或第三方复现后
再升级判断。
