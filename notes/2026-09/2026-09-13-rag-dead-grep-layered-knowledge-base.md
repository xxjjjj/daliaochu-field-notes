# RAG 已死还是 Grep 狂欢：企业知识库的分层终局

## 1. 这是什么

"AI 本体"系列第四篇公众号长文（群内以全文粘贴形式提供，无链接）。借"Coding Agent 不用向量库、只靠 Grep 就能玩转数十万行代码"的现象，回应"RAG 已死"的论战，给出企业知识库的折中架构主张：**RAG 与文件检索不是二选一，而是按知识性质分层，由 Agent 主动调度**。

- 发现入口：打捞处群内视频文字稿粘贴（原题为视频，非文章；2026-09-13 晶晶指出需先审题、核证据），无链接、无作者。

## 3. 审题：题目在说什么、证据从哪来（2026-09-13 核验）

**题面前半句"RAG 已死？"——确实是 2025 年真实热论，不是作者造的噱头。**
触发事件可考：2025 年 2 月 Claude Code 发布，代码导航直接用 ripgrep + glob，不建向量库；Claude Code 作者 Boris Cherny 公开说过早期试过本地向量库 RAG，"agentic search outperformed everything, by a lot"；Aider 作者 Paul Gauthier 撰文称给自主 coding agent 推荐 RAG 是"mind virus"，Aider 用 Tree-sitter + PageRank、零 embedding；Codex CLI 直接跑 ripgrep。HN 上有热帖"The RAG Obituary"。这是视频论据的真实出处。

**题面后半句"Grep 狂欢？"——同样真实，但狂欢本身也在被反驳。**
- Milvus 团队（向量库厂商，立场需打折）实测称 grep-only 在大仓库烧 token，做了 MCP 语义检索插件补位，自称省 40% token；
- RAGFlow 年终综述指出连代码检索都没有统一答案：Augment Code 不用裸 grep，而是微调专门的代码 embedding 模型；Cursor 也做代码索引而非纯 grep；
- ICML 2025 的 LaRA 论文（2326 测试用例 × 11 个模型）结论是"没有银弹"：对话类/泛查询 RAG 胜，Wikipedia 式 QA 长上下文胜，取决于模型、任务、语料。

**一个被多数论战参与者指出的概念偷换：** grep 本身就是检索——RAG 的 R（Retrieval）从没规定必须用向量。说"grep 取代了 RAG"在定义上不成立，准确说法是"向量切块流水线（ingest-chunk-embed-rerank）在代码场景被 agent 自主关键词检索取代了"。LightOn《RAG is Dead, Long Live RAG》、Algolia《No, RAG is not dead》、HN 高赞评论都是这个落点。

**视频的核心主张（分层底座）与业界合流方向一致：** Anthropic MCP 确实把静态文档暴露为 Resources、动态检索挂为 Tools；"Agentic RAG / RAG 降为 agent 的一个工具"是 2025 年主流演进，不是该视频原创。

**可信度评级：** 题面事实（Claude Code 用 grep、Cherny 表态、RAG 痛点）= 高，有多篇一手/二手佐证；"代码能 grep、业务文档不能裸 grep"的边界 = 高，各方无争议；"80% 高频需求转文件系统"= 无出处的口号，低；"Coding Agent 当骨架、LlamaIndex 当积木"= 厂商中立性存疑的工程主张，可参考不可照抄；MCP/Agentic RAG 趋势 = 高。

## 4. 核心观点

**Coding Agent 不用向量库的"四板斧"：**
1. 结构感知：先读 README / 索引表建立全局骨架；
2. 模式匹配：Grep 正则毫秒级锁定符号与锚链；
3. 分级精读：局部切片 + 按需滑动窗口，克制加载；
4. 规则索引：CLAUDE.md / AGENTS.md 等框架文件常驻上下文。
本质是从"被动灌入切块"转为"Agent 自主探索删节"。

**Naive RAG 的三个痛点：**
- 硬切块撕裂全局上下文（主条款与除外条款被切断）；
- 清洗、切分、重灌的持续维护噩梦，库沦为垃圾场；
- 语义相似 ≠ 逻辑相关，精确编号类查询经常失准。

**代码 ≠ 业务文档：** 代码符号一致性高、英文命名无歧义、格式规整；企业业务文档口语化、同义词缩写泛滥、载体是 PDF/表格/老系统。对几十万份杂 PDF 只给 Grep，要么同义词词典落空，要么盲目乱翻烧 token。

**主张的三层知识底座：**
1. **高频核心规则**（审批 SOP、准入基准、接口规范，通常不超几百页）→ 纯 Markdown + index.md 拓扑，Git 版本管理，Agent 扫骨架后局部精读，零向量化成本；
2. **海量长尾文档**（历史合同、旧报表、全量档案）→ 治理型 RAG 降维为 Agent 按需调用的 Tool，父子分块 / Late Chunking 处理复杂版面，强元数据骨架由模型在推理规划时自主触发；
3. **动态共识**（老专家口头规则、临时拍板口径）→ 沉淀为 Rules / 认知缓存文件，作为先验常驻上下文，免去重复检索。

**工程主张：** Coding Agent（运行时编排/操作系统）是现成骨架，LangChain/LlamaIndex 是按需引入的积木（非结构化处理与检索能力）；不要用积木从零拼骨架（"别用 LangChain 造 OpenHands"）。

## 5. 我学到了什么 / 与自有体系的对照

这篇的方向和我们已经在长的东西高度同构，可以当作外部印证：

- **我们的 Skill + SKILL.md 索引 + references/ 局部精读，就是第一层"文件拓扑"**；`hermes-agent-skill-authoring`、判例库方法（见 notes/2026-09/2026-09-13-case-library-above-rule-library.md）都要求索引先行、按需展开。
- **第二层在我们这里是 search_pack.py / search_culture.py 这类按需检索脚本 + MCP 工具**，而非常驻灌入；销售易 5415 条知识没有塞进上下文，就是"RAG 工具化"的实例。
- **第三层对应受治理的长期记忆与群内裁定口径**（如 CRM 权限"找丁一平/彩霞/园园"的确认人规则），专家指正即时沉淀、常驻先验。
- "代码可 Grep、业务文档不能裸 Grep"的边界判断是本文最有信息量的一段，比标题党的"RAG 已死"诚实：检索方式应由知识的符号一致性决定，而不是站队。

一个文章没说透的点：三层之间需要**失效与回流机制**——第三层共识过期、第二层文档版本更新后，第一层索引要跟着动，否则分层只是把垃圾场搬进三个房间。判例库笔记里的"'据'可回溯到现行文档 + 定期复核"正是补这个缺口。

## 5b. 2026 年新进展（2026-09-13 补查，回应"2 月太老了"）

争论起点是 2025-02，但到 2026 年中局面已经往前走了三步，视频文字稿没覆盖：

1. **"RAG 已死"作为口号基本熄火，收敛为"检索方式按任务分工"。** RAGFlow 2025 年终综述、多位从业者的说法一致：喊了两年"RAG 已死"，检索仍是生产 AI 系统的核心积木，变的是组织知识和检索的方式。SWE-bench 上朴素 chunk-RAG baseline 1.96%，2026 年 agentic 系统霸榜 80%+——被淘汰的是"无脑切块 top-k"这一种实现，不是检索本身。
2. **检索专用小模型成了新赛道（与"贵模型指挥便宜模型"同构，但关键在"专门训练"而非"随便拿便宜模型凑数"）。** Cognition（Devin/Windsurf）2025-10 发布 SWE-grep / SWE-grep-mini（一手：cognition.com/blog/swe-grep；Devin 官方文档）：用强化学习专门训练"多轮检索动作"的小模型，工具集收窄为 grep/read/glob，一轮并行多路搜索，只返回文件与行号范围，不负责答题；主模型（Sonnet 4.5）配它后任务完成数不变、端到端时间显著下降，且主模型上下文不被污染；mini 在 Cerebras 上 2800+ tok/s。Chroma 2026-03 发布 Context-1（20B），定位为 self-editing 检索 agent，号称检索基准追平 GPT-5/Opus 4.5、快约 10 倍、成本约 1/25（厂商自报，待独立复测）。本质是"图书情报专科资料员"：不是通用便宜模型兼职，而是 RL 训出的单一职能专科模型；同趋势还有 JSON 抽取专科模型 Schematron（8B/3B，比 GPT-5 便宜 40-80 倍）。对自有 harness 的含义：从"按通用能力分层"再进一步到"按职能专科化"。
3. **Google 2026-06 发布 OKF（Open Knowledge Format）**：把视频说的第一层"核心规则走 Markdown 文件拓扑"直接标准化——一个 vendor-neutral 开放规范，知识打包成带 YAML frontmatter 的 markdown 目录（bundle），git 可 diff、人可编辑、任何 agent 可直接遍历消费，无 SDK、无锁定。Google 官方称其形式化的就是 "LLM-wiki pattern"（一手：cloud.google.com 博客 + GitHub GoogleCloudPlatform/open-knowledge-format，v0.1）。**这与我们 Skill/llm-wiki 的目录+frontmatter+索引形态几乎同构，等于被 Google 追认为行业格式**；后续可评估我们的知识包是否对齐 OKF 字段。
4. **GraphRAG 经历一轮祛魅再定位。** 2024 年被捧的全量 GraphRAG 因索引成本和"很多真实任务还不如朴素 RAG"在 2026 年降温；LazyGraphRAG 把索引成本压到全量 GraphRAG 的 0.1%。共识定位：多跳关系推理、需要可解释链路的强监管场景（金融/法务/医疗）用图，单事实查找用向量/关键词，生产上以 query routing 做混合。网传"86% vs 32%"等对比数字多出自咨询/厂商博客，不作为实证引用。

**对原视频结论的修正：** 视频的三层底座方向在 2026 年不但没过时，第一层还被 OKF 标准化、第二层被"检索专员小模型"工程化了；但视频隐含的"通用大模型自己调度一切"正在被"大模型指挥专用小模型做检索"取代，这是它没赶上的最重要变化。

### 5b-补：检索专科模型在 RAG 场景的实际能力盘点（2026-09-13）

- **SWE-grep（Cognition 2025-10）只精代码**：训练环境全是代码仓库工具（grep/glob/read），未开放独立 API，仅嵌在 Windsurf Fast Context / Devin 内；不能平移到企业文档 RAG。
- **Context-1（Chroma 2026-03，20B，基座 gpt-oss-20b，权重开放）**：公开基准是 BrowseComp-Plus / SealQA / FRAMES / HLE（网页与通用多跳检索），非代码；号称追平 GPT-5/Opus 4.5、4 路并行比大模型单次便宜。但 agent harness 与进化代码发布滞后，社区反馈裸权重复现不了官方数字，"harness 占一半功力"；其训练基准含 Chroma 自产 benchmark，需独立复测；中文企业文档语料未验证。
- **路线有效性的独立旁证**：WebExplorer（8B，SFT+RL，16+ 轮网页搜索，BrowseComp 赢过更大模型）。
- **企业 RAG 当下真正规模化部署的"检索专科"是 reranker 精排模型**（Cohere Rerank 4、BGE Reranker v2；Databricks 报 +15pp 检索准确率），形态=混合召回+小模型精排；"小模型自主多轮翻文档"尚在早期，脏 PDF/表格/同义词/权限过滤都没被自动解决。
- 社区口碑：SWE-grep 正面但无法外部独立评测；Context-1 的 HN 讨论偏冷且有自评基准质疑。选型原则：看自家语料 A/B，不信厂商自报。
- 对自有知识云：中文文档场景暂不具备直接上 Context-1 条件；低成本可试点的是检索链路加 reranker，agentic 检索专员等中文/文档向开源版本与独立复测。
- **2026-09-13 结论：当前不上 reranker。** 现有 search_pack.py 是词面 n-gram 命中 + 手写加权（标题×6/别名×5/正文×1）+ 意图路由加分 + 人工 aliases，销售易语料符号规整、召回少而准，手写规则已在承担精排职能，再叠模型收益小且引入部署/数据外泄/精确匹配被语义干扰的成本。触发再评估的条件：①接入合同/制度/纪要等口语化业务文档；②出现"搜到了但排给我的不是那一条"的真实反馈（区别于"搜不到"，后者要补召回而非精排）；③召回结果量大到前几条需多屏翻阅。满足时先做历史问题 A/B（加/不加精排的 top5 命中率），正收益再上。

## 6. 它是否可信，哪些需要验证

可信的部分（方向性共识，非本文首创）：
- MCP 协议确实区分 Resources（静态资源暴露）与 Tools（动态能力调用），可查 Anthropic MCP 官方文档核实；
- Agentic RAG（由 Agent 规划检索而非单次 retrieve-then-generate）确为 2025 以来学界与工程界主流演进方向；
- Late Chunking / 父子分块是真实存在的检索工程技术。

需要保留的：
- "80% 高频需求转到文件系统"是经验口号，无数据支撑；企业不同岗位高频/长尾比例差异很大；
- "最高层领导临时拍板默认上浮 10%"被当作第三层示例——这类潜规则常驻风险极高（过期、误泛化、无法审计），共识层必须带生效日期、来源人和失效条件，不能裸写进常驻上下文；
- 文章未区分"检索不到"与"检索到了但模型不用"——很多企业 RAG 失败其实是引用遵从/答案合成问题，换 Grep 不解决；
- 对 LlamaIndex 的定位（纯数据层积木）略简化，它本身也有 agent/workflow 编排能力。

## 7. 对个人能力有什么价值

- 评审知识库/RAG 供应商方案时的追问清单：核心规则有没有轻量化承载？长尾检索是常驻灌入还是按需工具调用？切块策略是否保留条款级上下文（父子结构）？元数据谁维护、重灌成本谁担？共识失效机制是什么？
- 强化一个判断习惯：看到"X 已死、Y 才是终极"的标题，先拆两边各自成立的前提条件（本题即符号一致性与语料规整度）。

## 8. 对企业 AI 落地有什么价值

直接对应销售易/实施知识云下一步演进的参考架构：
- 第一层已经存在（Skill 化的规则、SOP、官方文档精编），继续把高频答疑口径 Markdown 化、索引化；
- 第二层目前是本地 search_pack.py，后续若接入更大量历史文档（旧合同、实施交付档案、工单），应做成 Agent 按需调用的检索工具并配强元数据，而非扩常驻上下文；
- 第三层（管理者裁定口径）已有治理入口（群内确认 → 记忆/Skill），但要补"生效日期 + 来源 + 复核期"字段，防止临时口径永久化。
- 给业务方讲知识库时可直接用这个三层比喻：常用制度放书架（自己走过去翻）、历史档案进档案库（开条让管理员调）、老板口头规矩写进交接班本（带日期）。

## 9. 可做的小实验

暂不开新实验。待有真实需求时可做：取一批销售易高频问答，对比"纯文件拓扑检索"与"现有 search_pack 语义检索"在精确编号类问题（如条款号、字段名）上的命中率——文章主张这类问题文件检索更强，值得用我们的语料实测而不是直接信。

## 10. 风险和边界

- 若按本文落地，最大风险是第三层"潜规则常驻"：无审计、无失效、把个人口径固化为组织规则；必须治理化（来源、日期、复核）。
- 第一层 Markdown 化的隐性成本是人工治理——"几百页核心制度"的维护责任不落部门，文件拓扑会迅速腐化，这与 RAG 垃圾场是同构风险。
- 业务文档 Grep 不可行的结论在中文口语化语料上成立，但反过来"语义检索万能"同样不成立；精确匹配（编号、专有名词、字段 ID）仍应留给字面检索，混合检索是工程现实。

## 11. 当前结论

标题是论战，正文是折中：它真正有价值的论点不是"RAG 已死"，而是"**知识按性质分层、检索权交给 Agent 按需调度**"。三层底座与自有体系（Skill 文件拓扑 / 按需检索脚本 / 受治理记忆）基本同构，可作为对外讲解知识库架构的通俗版本和供应商评审清单；无作者无链接，引用业界事实时回一手来源（MCP 文档、Agentic RAG 论文），不转引本文口号。
