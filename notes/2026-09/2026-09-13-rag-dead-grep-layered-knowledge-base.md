# RAG 已死还是 Grep 狂欢：企业知识库的分层终局

## 1. 这是什么

"AI 本体"系列第四篇公众号长文（群内以全文粘贴形式提供，无链接）。借"Coding Agent 不用向量库、只靠 Grep 就能玩转数十万行代码"的现象，回应"RAG 已死"的论战，给出企业知识库的折中架构主张：**RAG 与文件检索不是二选一，而是按知识性质分层，由 Agent 主动调度**。

## 3. 核心观点

**Coding Agent 不用向量库的"四板斧"：**
1. 结构感知：先读 README / 索引表建立全局骨架；
2. 模式匹配：Grep 正则毫秒级锁定符号与锚链；
3. 分级精读：局部切片 + 按需滑动窗口，克制加载；
4. 规则索引：CLAUDE.md / AGENTS.md 等框架文件常驻上下文。
本质是从"被动灌入切块"转为"Agent 自主探索删节"。

**Naive RAG 的三个痛点：**
- 硬切块撕裂全局上下文（主条款与除外条款被切断）；
- 清洗、切分、重灌的持续维护噩梦，库沦为垃圾场；
- 语义相似 ≠ 逻辑相关，精确编号类查询经常失准。

**代码 ≠ 业务文档：** 代码符号一致性高、英文命名无歧义、格式规整；企业业务文档口语化、同义词缩写泛滥、载体是 PDF/表格/老系统。对几十万份杂 PDF 只给 Grep，要么同义词词典落空，要么盲目乱翻烧 token。

**主张的三层知识底座：**
1. **高频核心规则**（审批 SOP、准入基准、接口规范，通常不超几百页）→ 纯 Markdown + index.md 拓扑，Git 版本管理，Agent 扫骨架后局部精读，零向量化成本；
2. **海量长尾文档**（历史合同、旧报表、全量档案）→ 治理型 RAG 降维为 Agent 按需调用的 Tool，父子分块 / Late Chunking 处理复杂版面，强元数据骨架由模型在推理规划时自主触发；
3. **动态共识**（老专家口头规则、临时拍板口径）→ 沉淀为 Rules / 认知缓存文件，作为先验常驻上下文，免去重复检索。

**工程主张：** Coding Agent（运行时编排/操作系统）是现成骨架，LangChain/LlamaIndex 是按需引入的积木（非结构化处理与检索能力）；不要用积木从零拼骨架（"别用 LangChain 造 OpenHands"）。

## 4. 我学到了什么 / 与自有体系的对照

这篇的方向和我们已经在长的东西高度同构，可以当作外部印证：

- **我们的 Skill + SKILL.md 索引 + references/ 局部精读，就是第一层"文件拓扑"**；`hermes-agent-skill-authoring`、判例库方法（见 notes/2026-09/2026-09-13-case-library-above-rule-library.md）都要求索引先行、按需展开。
- **第二层在我们这里是 search_pack.py / search_culture.py 这类按需检索脚本 + MCP 工具**，而非常驻灌入；销售易 5415 条知识没有塞进上下文，就是"RAG 工具化"的实例。
- **第三层对应受治理的长期记忆与群内裁定口径**（如 CRM 权限"找丁一平/彩霞/园园"的确认人规则），专家指正即时沉淀、常驻先验。
- "代码可 Grep、业务文档不能裸 Grep"的边界判断是本文最有信息量的一段，比标题党的"RAG 已死"诚实：检索方式应由知识的符号一致性决定，而不是站队。

一个文章没说透的点：三层之间需要**失效与回流机制**——第三层共识过期、第二层文档版本更新后，第一层索引要跟着动，否则分层只是把垃圾场搬进三个房间。判例库笔记里的"'据'可回溯到现行文档 + 定期复核"正是补这个缺口。

## 5. 它是否可信，哪些需要验证

可信的部分（方向性共识，非本文首创）：
- MCP 协议确实区分 Resources（静态资源暴露）与 Tools（动态能力调用），可查 Anthropic MCP 官方文档核实；
- Agentic RAG（由 Agent 规划检索而非单次 retrieve-then-generate）确为 2025 以来学界与工程界主流演进方向；
- Late Chunking / 父子分块是真实存在的检索工程技术。

需要保留的：
- "80% 高频需求转到文件系统"是经验口号，无数据支撑；企业不同岗位高频/长尾比例差异很大；
- "最高层领导临时拍板默认上浮 10%"被当作第三层示例——这类潜规则常驻风险极高（过期、误泛化、无法审计），共识层必须带生效日期、来源人和失效条件，不能裸写进常驻上下文；
- 文章未区分"检索不到"与"检索到了但模型不用"——很多企业 RAG 失败其实是引用遵从/答案合成问题，换 Grep 不解决；
- 对 LlamaIndex 的定位（纯数据层积木）略简化，它本身也有 agent/workflow 编排能力。

## 6. 对个人能力有什么价值

- 评审知识库/RAG 供应商方案时的追问清单：核心规则有没有轻量化承载？长尾检索是常驻灌入还是按需工具调用？切块策略是否保留条款级上下文（父子结构）？元数据谁维护、重灌成本谁担？共识失效机制是什么？
- 强化一个判断习惯：看到"X 已死、Y 才是终极"的标题，先拆两边各自成立的前提条件（本题即符号一致性与语料规整度）。

## 7. 对企业 AI 落地有什么价值

直接对应销售易/实施知识云下一步演进的参考架构：
- 第一层已经存在（Skill 化的规则、SOP、官方文档精编），继续把高频答疑口径 Markdown 化、索引化；
- 第二层目前是本地 search_pack.py，后续若接入更大量历史文档（旧合同、实施交付档案、工单），应做成 Agent 按需调用的检索工具并配强元数据，而非扩常驻上下文；
- 第三层（管理者裁定口径）已有治理入口（群内确认 → 记忆/Skill），但要补"生效日期 + 来源 + 复核期"字段，防止临时口径永久化。
- 给业务方讲知识库时可直接用这个三层比喻：常用制度放书架（自己走过去翻）、历史档案进档案库（开条让管理员调）、老板口头规矩写进交接班本（带日期）。

## 8. 可做的小实验

暂不开新实验。待有真实需求时可做：取一批销售易高频问答，对比"纯文件拓扑检索"与"现有 search_pack 语义检索"在精确编号类问题（如条款号、字段名）上的命中率——文章主张这类问题文件检索更强，值得用我们的语料实测而不是直接信。

## 9. 风险和边界

- 若按本文落地，最大风险是第三层"潜规则常驻"：无审计、无失效、把个人口径固化为组织规则；必须治理化（来源、日期、复核）。
- 第一层 Markdown 化的隐性成本是人工治理——"几百页核心制度"的维护责任不落部门，文件拓扑会迅速腐化，这与 RAG 垃圾场是同构风险。
- 业务文档 Grep 不可行的结论在中文口语化语料上成立，但反过来"语义检索万能"同样不成立；精确匹配（编号、专有名词、字段 ID）仍应留给字面检索，混合检索是工程现实。

## 10. 当前结论

标题是论战，正文是折中：它真正有价值的论点不是"RAG 已死"，而是"**知识按性质分层、检索权交给 Agent 按需调度**"。三层底座与自有体系（Skill 文件拓扑 / 按需检索脚本 / 受治理记忆）基本同构，可作为对外讲解知识库架构的通俗版本和供应商评审清单；无作者无链接，引用业界事实时回一手来源（MCP 文档、Agentic RAG 论文），不转引本文口号。
