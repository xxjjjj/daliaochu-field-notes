# WeChatBridge（微信流）：官方通道的聊天记录中转站

## 1. 这是什么

WeChatBridge（微信流）是一个把微信聊天记录「收—存—投」的中转站工具：在微信里多选消息 → 合并转发到其他应用 → 微信流接收 → 投递给各家 AI App（ChatGPT、Claude、豆包、千问、WorkBuddy、DeepSeek 等）或沉淀为 Obsidian Markdown 笔记。已有 macOS、Windows 端，iOS 版文章宣称开发完成、正在 App Store 提审；安卓、鸿蒙在路线图上。

项目基于另一个开源项目 Dukou（qzz0518/Dukou）二次开发，MIT 协议。仓库本体真实、活跃：截至 2026-11-05 核实，1.9k star / 525 fork / 172 commits（文章发布时称 1.7k star，仍在增长），目录含 macos/（SwiftPM）、ios/（XcodeGen，复用同一 Core）、windows/（.NET WPF）、shared/，有 Tests、SECURITY.md、THIRD-PARTY-NOTICES.md，工程完整度高于一般个人项目。

## 3. 核心观点 / 核心能力

1. **走的是微信官方口子，不是逆向。** 机制依赖微信自身的「合并转发 → 转发到其他应用」：微信导出一个含 聊天记录.txt + 图片/视频/附件的 ZIP，系统分享面板交给带 Share Extension 的应用。不读数据库、不注入、不破解、不碰微信进程。评论区「会不会被封」的疑问，作者三次回复均强调这是官方支持的分享通道。
2. **产品形态极简：只做收、存、投三件事。** 收（分享扩展存入收件箱，弹卡片即回微信）、存（按卡片管理，可像微信一样查看、图片内联）、投（选目标 App + 场景提示词，支持多批合并、自动去重）。
3. **绕平台限制的工程细节真实。** iOS 分享扩展不能替用户打开别的 App、不能自动粘贴，最后一下必须人点；豆包/千问不收 ZIP，就统一转成图片插入对应消息下方的 PDF 保证各家都能吃；微信单次转发上限 100 条，做了分批收集（自动复制每批最后一句话用于回微信定位接续）。
4. **Obsidian 沉淀是「以后还能用」的存。** 输出整理好的 Markdown：聊天名/场景/条数抬头、每条保留发送人与时间、图片内联、附件和原始 ZIP 进附件文件夹，本地文件可搜、可双链，不依赖微信存续。
5. **安全设计有明文边界。** Share Extension 在沙盒中运行且无网络权限；数据只来自微信主动导出的文件、只存本机；屏幕录制权限仅用于识别聊天名、图像只在内存处理；辅助功能权限仅用于激活目标 App 和粘贴。

## 4. 我学到了什么

### 4.1 方法论：别跟 Agent 聊需求，跟它定验收

文章最有迁移价值的不是工具本身，而是作者用 Claude Code + Kimi K3.1 Pro 开发 iOS 版的工程组织方式，号称 18 个工作日的计划 6 个多小时跑完：

- **先写计划再写代码。** 第一轮提示词只定产品形态和平台约束（哪些 iOS 做不到要提前标），要求模型先复述理解、列疑问，不许猜。
- **两份文档当总线。** 开发技术文档（700+ 行，工作规则、输入规格、架构、模块规格、任务清单 T0–T9）+ 档期文档（里程碑 M0–M6，每个里程碑带「出口闸门」）。任务编号与验证编号一一对应，目标读者设定为「任何一个 Agent 只读这两份就能做完」。
- **验证分模拟器（S1–S11）与真机（R 系列）两档。** 每条写死操作步骤和通过标准，例如「分享 0 字节文件必须提示失败不能存入」「删卡片后 5 秒内撤销必须恢复」「杀进程后再分享，重开必须看到新卡片」。
- **硬规矩保不退化。** 只在 worktree 改、每任务单独提交且标题带 [AI]、不 push；动到 macOS 共享 Core 必须跑通原有 186 个测试；做不到验证的写「待真机」，不许标通过。
- **模型自验收自抓 bug。** 空文件入库、卡片点不开、分组计数 2/1 错误、按钮被标签栏遮挡等问题都是模型在跑验收时自己发现、自己记录现象/原因/修复提交。

这套做法与「贵模型出计划、便宜模型执行、Markdown 文档当总线」的多 harness 协作模式同构，可直接迁移到内部 Agent 开发任务的验收设计。

### 4.2 路线对比：主动操控 vs 官方通道

同期出现的手机端 Agent（如 Mika，见同库 2026-11-05 笔记）走「无障碍服务 + 虚拟屏主动操控任意 App」路线，能力强但处于平台灰区、有账号风控；微信流走「只接官方分享出口、被动中转」路线，能力边界清晰（不能自动读未读、不能自动回复、不能免手点），但合规姿态稳。两者代表了手机侧自动化的两个极端：**灰区换能力 vs 合规换安全**，评估同类工具时先分清它站在哪边。

## 5. 它是否可信，哪些需要验证

可信度分层：

- **仓库与机制层面可信（已核实）。** 仓库真实、MIT、工程结构完整、安全声明具体到权限用途；机制确实基于微信官方分享能力，不依赖越狱/root/注入。
- **文章中的模型效果宣称待独立验证。** 「Kimi K3.1 Pro 国产开源第一梯队、AA 评测 55 分、6 小时干完 18 人日」均为作者单方叙述，且作者在文中强烈安利该模型、文末还引导去各渠道使用，存在软文属性；额度消耗快的问题作者承认且称官方已给补偿方案。模型实测表现需自行压测，不能把作者口径当结论。
- **iOS 版状态待核。** 文章称开发完成、提审 App Store；但 GitHub README（11-05 核实）仍写「iOS 版正在开发中」，仓库 ios/ 目录存在但未见 App Store 上架链接。在上架前，体验资格通过作者微信群分发，属于非正式分发渠道。
- **评论区需求暴露能力边界（真实用户反馈，可参考）。** 自动读未读并给回复建议（客服场景）、企业微信支持、几十万条历史记录批量导出，目前均不支持；其中「自动读取/回复」受微信开放能力限制，短期看不到官方路径。

## 6. 对个人能力有什么价值

- 提供了一份可照抄的 **Agent 验收驱动开发模板**：出口闸门、S/R 两档验证、「待真机不许标通过」的诚实规则、固定格式进度汇报。下次给 coding agent 派复杂活时，先产出这两份文档再开工。
- 个人知识管理场景立即可用：把高价值群聊（项目群、客户群、学习群）定期转成 Obsidian 本地 Markdown，解决微信收藏「存了就埋」的问题，且数据在自己手里。

## 7. 对企业 AI 落地有什么价值

- **销售/客户经营场景**：客户群聊一键「客户复盘」，自动列要点、结论、待办、风险、负责人、截止时间；需求沟通原话本地归档，降低口头承诺扯皮成本。这是文章演示的真实场景，与销售型组织的客户管理痛点直接对应。
- **信息减负场景**：资料群、家长群式的刷屏群，通勤路上手机转发即出摘要，把「爬楼」变成可委托的动作。
- **合规红线要先划**：企业聊天记录含客户信息、报价、合同条款，转发给第三方公有 AI 前必须有脱敏规则和准入要求；工具本身只保证「不经过作者服务器」，但投递的最后一跳去了哪家 AI、数据如何被使用，取决于所选目标的隐私条款。企业若采用，应先限定允许的投递目标（优先企业版/私有化端点），禁止把含客户数据的记录投给个人版消费级 AI。
- 不适合作为客服自动应答的基础组件：它是手动触发的中转，不是实时监听/自动回复，评论区的此类期待属于另一类系统（且合规难度高一个量级）。

## 8. 可做的小实验

1. macOS 端小范围实测：用本人工作微信的一个低敏感群，走完整链路（多选→转发→投递给一个 AI→再沉淀一份 Obsidian），核对消息条数、时间戳、附件完整性与 100 条分批合并的去重效果。
2. 把第 4.1 节的验收驱动模板抽成一份内部《Agent 开发任务书模板》（技术文档 + 档期文档 + S/R 验收清单），在下一个内部脚本/工具开发任务上试用，对比「直接聊需求」的返工率。
3. 等 iOS 版正式上架 App Store 后再评估手机端（提审期间的群分发版不建议装工作机）。

## 9. 风险和边界

- **数据安全（最高优先）**：聊天记录是敏感数据富矿。工具本地化设计降低了中间层风险，但投递目标 AI 的数据政策是另一回事；企业用途需先定脱敏与准入规则，作者文末免责声明也明确要求脱敏、仅处理有权使用的记录。
- **账号与合规**：虽走官方分享通道、不注入不破解，但微信对第三方工具的政策可能变化，分享口子本身依赖微信版本（macOS 需微信 4.1.13+）；工具声明仅供学习测试交流，商用边界需自行评估。
- **供应链**：桌面端安装包走蓝奏云、iOS 提审期走社群分发，没有签名公证的统一发布通道；谨慎做法是对照 GitHub 源码自行构建（仓库提供 make-app.sh / install-dev-build.sh），不装来源不明的二进制。
- **能力边界**：手动逐条多选、单次 100 条上限、不支持自动读取/回复、不支持企业微信、无安卓/鸿蒙（截至发稿）；几十万条历史消息的全量导出不是它的设计场景。
- **成本**：作者反馈 Kimi K3.1 Pro 长程任务额度消耗快；6 小时连续跑模型的 token 成本在规模化使用前要实测。
- **模型口径风险**：文章对 Kimi 的评价带推广属性，选型不要锚定单一模型，同类长程编码任务应跨模型压测。

## 10. 当前结论

微信流是「合规通道派」手机数据自动化的代表性开源项目，仓库本体可信、机制干净、工程完整，工具价值与方法论价值都成立：工具侧适合个人知识沉淀和低敏感群聊摘要，企业侧必须先补脱敏与投递准入；更大的收获是它完整演示了「定验收而非聊需求」的 Agent 工程范式——出口闸门、两档验证、不许假装通过——这套方法比工具本身更值得抄走。iOS 上架状态、模型效果宣称、蓝奏云分发的供应链三项保持待验证。
