# All Code Is Slop (Except Mine)：把每次纠正变成可执行检查

## 1. 这是什么

Lauren Tan（网名 poteto，自称 Potato），SpaceXSI（xAI）Principal Engineer，Grok Bot 团队成员。
2026-11-11 在旧金山 AI Engineer CODE 2026 主舞台讲了约 17 分钟（日程 10:10–10:30，实际提前约
10 分钟开讲）。官方录像 2026-11-14 上传 YouTube，至核验时 33.5 万次观看。

**一句话论点**：agent 写的代码要能在每天几百个 PR 的量级上不掉质量，前提是**每一次纠正都被
编码成代码库里的确定性检查**，而 review 的对象从 diff 换成验证产物；给一个 sloppy 的循环做
自动化，只会更快更贵地生产 slop。

这次核验的一手源非常完整：官方 talk 页（结构化解读）+ 会议现场的机器逐字稿（The-Focus-AI
仓库，qwen3-asr 转录，标注了不可靠词）+ YouTube 官方录像描述里的字幕片段。因此本卡片的内容
以逐字稿为准，二手稿仅作发现入口。

## 3. 一手内容全貌（按演讲时间轴，逐字稿为准）

**00:24 开场**：举手——"有多少人看过别人写的代码，心想这都是 slop？"我也一样。
但今天我要说服你：slop 可以变成金子。

**01:40 从产量到信任**：上个月我向生产发了 3,000 个 PR。在 agents 之前我们不太在意产量，
只在意离群值——前公司把这种人叫 "coding machines"，比如一个周末重写整个 Google Apps 的
Brett Taylor。现在**任何人都可以是 coding machine**。她的论点：软件工程师的元工作（the meta）
是"在极大提高生产力的同时，维持甚至提高代码质量"。有人管这叫 software factory，她更愿意
说得简单——**全部关于信任，但不是盲信，而是投资 agent 的环境**。她花了 6 个月才到能
每天合几千个 PR 的程度，"你会比我快得多"。

**02:55 从低信任到高信任：倒金字塔**（inverse pyramid，这是全场骨架，二手稿把它压扁了）

1. 第一层——代码本身：好的 API 设计、架构、重构（确定性）
2. 第二层——静态手段：lint 工具、类型系统、编译器、各种测试（确定性）
   → 前两层合起来**约束 agent 能做什么，逼它默认做对**
3. 第三层——验证：runtime 验证 + 形式化验证，找 bug、检查不变量、检查 agent 是否真的理解了
   你的目标和意图
4. 第四层（最薄的一层）——**一点点 prose**：rules、skills、AGENTS.md，"留给需要判断的事"

她的操作准则：因为 agent 的输出基于输入，而**codebase 是 agent 最大的输入之一**，所以每次
纠正 agent 时，先想"怎么把它变成确定性检查"，而不是"再往 rules / AGENTS.md 加一行"，因为
代码里更可复现，也就更可信任。

**04:26 代码库是一座花园**：2024 年上班，一天 review 同事写的 3 个 PR；今天是 300 个。
每个工程师现在是一支几百甚至上千 agent 的团队，代码像连续流、像活物。你设的约束和护栏就是
混凝土基础，新代码绕着它长。**所以工程工作某种意义上变成"收垃圾"**：任何 workaround、
anti-pattern、废弃代码、技术债，现在都会被下一个 agent 复制，因为它看起来像这个库里既定的
做法——就像花园里的杂草和害虫，一转眼长满。结论：把代码库弄得越干净，agent 抄的就越对。

**05:56 Dune 与"有机架构"**：Dune 是为 GrokBot 自研的客户端框架，"技术上不惊艳，可以理解成
Electron 版的 Next.js"，价值在于**把做桌面应用踩过的坑编码成约束**。两个例子：

- **useEffect**：凡是"需要 nuance 才能解对"的东西，通常会被误用；useEffect 有正当用途但常被
  滥用，而 **agents 不擅长 nuance**。做法：产品代码里禁掉，只在 Dune API 内部少数地方允许。
  效果是这类问题被**分类别地消灭**（categorically eliminated），再也不用在 code review 里抓一次。
- **目录即上下文**：Cursor（Electron 应用）的典型 anti-pattern 是把主进程代码 import 到渲染
  进程，导致长任务和卡顿。GrokBot 和新应用里两个顶级目录直接叫 `electron-main` 和
  `electron-renderer`，跨目录 import 被依赖图分析器禁止。规则设置很简单，但**少了一件 review
  时需要想的事**。

**07:54 agent 与 markdown / 注释**：一个意外发现是 agent 爱用 markdown（文档、代码注释、
rules、skills）来写"我为什么不这么做"的辩护，或者对一次小纠正过度反应、当成永远不能破的铁律。

最典型的案子：Cursor 里 agent 超爱用命令式计时器（`setTimeout` / `requestAnimationFrame` /
`requestIdleCallback`）做快速修复，其实是在给"VS Code 命令式风格 vs React 声明式风格"的架构
冲突打补丁——而这个架构选择让客户端和用户性能都变差；计时器被大量快速创建销毁会引发频繁
major GC，直接卡顿。**最糟的是 agent 写了大量注释解释"这个 quick fix 为什么合理"**，然后补丁
遍地。GrokBot 的教训：禁掉 99% 的注释，理由四条——容易过期；人本来就不读；给 agent 一个
"不做对的事"的逃生口；**以及最关键的：注释不可执行**（not enforceable）。现在改成 lint 规则
给出好的错误信息，直接告诉 agent 去修根因。

一般原则：**每次纠正 → 一条确定性检查，或者通过更好的 API 设计 / 架构把整类问题消灭**。
做够多次之后，review 要盯的东西越来越少，到某个点你会发现没什么可 review 的，可以让 agent
合并大部分 PR。

**10:40 验证**：他们的 code review 已经缩成"看验证产物"——视频、截图、图、形式化验证结果。
- 最基础是 runtime verification，说白了就是**给 agent 一个自己能跑代码的方式**，用人类开发者
  也在用的调试工具（如 Chrome DevTools Protocol）。
- **feature map**：从用户视角给应用做一张功能快照，于是你说"左边侧栏那个东西"时 agent 不用猜。
- **自研 CLI + driver**：agent 每次复用同一套，省 token，而且自身可测试。
- **形式化验证**：TLA+ 做 model checking，覆盖"多设备多平台通知"这类主要用户流；Lean 用于
  剪枝/验证特定算法，例如自研虚拟化库，检查不出 flicker / jitter。仍在实验，"已经找到不少 bug，
  但肯定不是银弹"，是又一层工具，不是替代品。
- 还在试 **property-based testing 用于 UI**（用的库名在转录里不可靠，不作为事实）。

**12:50 token 花在哪**：引 Cindy 的一条推文——6 个月前她说没法信任 agent，因为有 subtle bug
被合进去，缺的正是验证流程；6 个月后她说**每天 70% 的 token 花在验证上**。"这跟我看到的一致"。
关键判断：这些技术**没有一个是新的**，都是好软件工程，只是以前太贵（难懂、难维护），agent 把
成本大幅降下来了——"我们正进入软件测试和应用的黄金时代"，可以测到过去经济上不可行的程度。
她自己在 pstack 里做了 **Statechart skill**：从用户视角可视化状态机，配合视频和截图审阅；
官方 talk 页补了一句关键区别——**一张"成功状态"的截图说明不了有哪些状态、允许哪些转移**。

**14:22 应许之地**：GrokBot 团队上月向生产发了 11,000 个 PR；大约每天出一个稳定版；核心团队
产出大幅提高；还有大量 drive-by 贡献者（没多少上下文也在提）；**10 月有约 227 人至少贡献
1 个 PR**。尽管如此，revert 的比例在**相对值上反而下降**，稳定在约 0.5%。更值得注意的不是
"没崩"，而是**性能多个维度比发布时更好**：启动、打字、开对话、切对话都更快。她也提醒：
GrokBot 仍是 Electron 应用，有天花板，但已经比很多 AI 创业公司快。

**16:10 建工厂之前**：在你冲去自动化一切之前——每次纠正 agent，先尽量通过改代码库防止这类
anti-pattern 再出现，再清掉旧的模式，然后确保验证故事足够强。这些本来就是自动化的前提。
**"如果你的内循环在产 slop，自动化这个循环只会产出更多 slop"**，还要往里扔越来越多 token。
反过来，做完这些投资后，很多事变得可能：GrokBot 有大量 connectors 和 routines 可以拉起
Cursor Cloud agents 和 projects，编排几百甚至几千个 agent。例子：每次发新版本，GrokBot 自动
起一个 Cursor 项目去 fuzz 整个构建，**像真实用户一样用应用找 bug**，为每个 bug 开修复 PR 并
自动合并——"听起来很疯，但那是因为我们的代码库足够好，PR 默认就是好的，大多数上线的产品代码
不再需要深度人工 review"。

收尾原话："当你有扎实的基础和良好的有机架构，你可以把 slop 变成金子，并且在不牺牲质量的前提下
以高质量、高速度交付。我叫 Potato，也叫 Lauren。"

## 5. 二手稿（抖音 AI小圆）核验与勘误

二手稿本身是"已逐句校对"的 ASR 版本，比一般二创严谨，方向基本对；但对照一手逐字稿仍有
几处结构性失真，其中两处会直接把人带错。

**成立的部分**：3000 / 11000 / 0.5% / 6 个月 / 一天一个稳定版 / "不是排行榜，是他们团队的结果"
全部与一手一致；"每次纠正变成一条检查""从 API 架构上消掉这类错误""规则像杂草不拔就长"
"主进程不许引用渲染进程、靠目录和依赖分析在工具层拦""外循环是自动 fuzz → 自动提 PR → 自动合并"
"先夯实内循环再自动化"——都对。**她把"她个人 3000"和"团队 11000"分清了，这点比多数英文侧
拆解还准。**

**要纠正的**：

1. **"GrokBot 负责人"——拔高**。一手是 Grok Bot 团队的 Principal Engineer（"I work on GrokBot at
   SpaceXSI"），全场没有"负责人/founder/lead"的说法。同一错误在本仓库 2026-11-10 那张卡的二手
   视频里已出现过一次，属高频误传。
2. **"内循环三件套"丢掉了倒金字塔的骨架**。一手是四层、且前两层是确定性的（代码本身 + 静态
   分析），**prose（rules/skills/AGENTS.md）是最薄、最靠后的那层**。二手稿把它写成并列的
   "三件套"，恰好丢掉全场最反直觉、也最值钱的那句话：规则应该是你花时间最少的地方，
   而多数团队恰恰把 AGENTS.md 写成了最厚的一层。
3. **用了 useEffect 这个最典型的例子却整段丢了**，只保留了主进程/渲染进程那一条。而且一手明确
   限定：这是他们的**本地架构选择**，不是宣称 useEffect 普遍有害——二手稿容易让人反向抄成
   "禁 useEffect"。
4. **"禁 99% 注释"被 ASR 打散成"产品代码因为太吃卡住注释〔识别不清〕"**，四条理由只剩"人不读"。
   一手的四条是：易过期 / 人不读 / 给 agent 逃生口 / **不可执行**。最后一条才是论点（下节详述）。
5. **形式化验证整段丢失**（二手稿自标"此段识别严重失真"）。一手是 TLA+ 做多设备通知流
   model checking、Lean 验证自研虚拟化库防 flicker、property-based UI testing，并且**她明确说
   "不是银弹"**。二手稿把它概括成"把对不对变成机器可判定的结果"，比原话更强、更绝对。
6. **漏掉 feature map 和自研 CLI/driver**——这是 runtime verification 里唯一能直接抄走的两件
   东西（给 agent 一张用户视角地图 + 一套可复用的操作工具）。
7. **漏掉 227 人贡献者和"性能反而变好"**。后者是整场最有说服力的反向指标：通常大家担心高速
   产出会拖慢产品，他们的情况是启动/打字/切对话都更快。
8. **漏掉 70% token 花在验证上**。这是全场唯一可当预算决策依据的数字。
9. **漏掉 Statechart skill**（在她自己的 pstack 插件里），正好接上本仓库 2026-11-10 那张卡。
10. **"很多是睡着的时候合上的"**：二手稿当事实陈述，但这句对应的逐字稿位置是 ASR 乱码
    （"A lot of them can't speak"），逐字稿不可核；英文侧 TestSprite 等转述也这么写，可能在
    幻灯片上。**可讲，但别当原话引用。**

**二手稿附带的"给你的提炼"里有一处不能照抄**：它把 0.5% revert 率建议成"可用的验收线"。
0.5% 是在 11,000 PR/月、有 CI 与自动化测试、跑了 6 个月的团队里长出来的**团队自报相对值**，
不是可移植 KPI；且我们做 CRM 配置/RPA 运维没有 revert 这个动作。要换成本地等价物（见第 7 节）。

## 6. 我学到了什么

- **这篇的真正命题不是"少写规则"，是"规则的载体要在能执行的地方"**。"注释不可执行""prose 是
  最后一层"这两句话合起来是一条判据：一条知识如果写成文字，它对下一次执行的约束力接近零；
  写成检查，它才变成不变量。本仓库的 `notes/`、Skill、AGENTS.md 全部落在"prose 层"，
  这条判据直接适用于我们自己的体系，不止适用于写代码。
- **"agent 会复制它看到的既定模式"是比"提示词写得好不好"更底层的机制**。花园比喻的成本含义是：
  遗留的 workaround 不是历史债，是**未来产出的样本**。清理旧模式属于提高未来产出质量，不是还债。
- **注释/文档会变成借口**，这条对我们有直接映射：Skill 里写"注意不要 X""尽量别 Y"，实际效果
  等同于给 agent 一个"我知道但这次例外"的许可。同样一句话，写成"正确路径 + 检查命令"，
  行为差别很大。
- **review 的对象从 diff 换成验证产物**（视频、截图、状态图、形式化结果）。这对非代码领域同样
  成立：审一份 AI 产出的报告/PPT/配置，应该要求它交"实跑输出"，而不是让我读它的自述。
- **顺序论比结论更重要**：先内循环（检查、约束、验证），再外循环（并行/自动合并）。反了就是
  "更快更贵地产 slop"。这一条与本仓库 2026-11-19「智能负债 / Skill 半衰期」、2026-11-11
  「TDD + 形式化验证 vs 对抗式 review」三篇指向同一件事，可以合成一条方法论。
- **形式化的诚实边界**：她自己在用 TLA+/Lean，仍然说"不是银弹"。这类一手表述比任何二手
  总结都更有参考价值——**看到有人做了重投入还说"这只是又一层"，通常说明这一层真的不是必需项。**

## 7. 对个人能力 / 企业 AI 落地的价值

**可以直接搬的三件，按成本从低到高：**

1. **prose 审计（零成本，本周可做）**：把现有 Skill / 记忆 / AGENTS.md 里所有"必须""不要"
   条款过一遍，分三类——① 能被脚本或 API 卡住的；② 能被字段/权限/流程配置卡住的；
   ③ 只能靠判断的。① 和 ② 应该搬出 prose 变成检查，③ 才留在文字里。我们现有条款里就有
   明确属于 ① 的：群里 @人必须用 post 富文本（可封装成唯一发送脚本）、凭证不许明文
   （可脚本扫描）、周期库查询必须 `ORDER BY date`（可写进查询函数）、知识云检索必须先分领域
   （可写路由函数）。**这些现在靠"我记得"，等于把可执行的约束放在最弱的一层。**
2. **给每个自动化任务加"验证产物"要求（半天）**：交付标准从"做完了"改成"交出可复核的证据"
   （实跑输出、API 返回、截图、变更前后的字段值）。这跟 pstack 的 verify 要求是同一件事。
3. **本地化验收指标（需口径协商）**：把"回滚率"换成本组可测的等价物——**变更回退率 /
   二次修正率 / 返工工时**。不适合直接搬 0.5%，但"看回退与返工、不看提交量"这个方向完全适用。

**需要条件的**：形式化验证（TLA+/Lean）在我们的场景不成立，也不必要；真正对应的是"让 agent
自己能跑一遍并留下证据"，这是 runtime 那层，成本低得多。

**明确不建议照搬的**：自动 fuzz → 自动提 PR → 自动合并的闭环。它成立的前提是 CI、测试覆盖、
依赖图分析、6 个月的环境投资和一个 227 人贡献的代码库，我们没有这些基建。

## 8. 可做的小实验（未执行，待拍板）

- **A｜prose→检查迁移审计**：统计现有 Skill/记忆里可脚本化条款占比，选 3 条改成脚本或唯一入口，
  两周后看"同类问题复发次数"。零算力成本，纯工程。
- **B｜验证产物交付制**：挑一个高频自动化（如每日简报 / 周报 / 群里答疑），要求每次交付附
  实跑证据，观察返工轮次变化。
- **C｜状态图替代截图**：给一个多人状态的流程（公海池流转、审批分支）画状态机图而非单张
  截图，看是否更容易被 review 出漏洞——这是 Statechart skill 思路的非代码版移植。

以上仅为候选，未获明确指令前不动手。

## 9. 风险和边界

- **规模与前提不可移植**：11,000 PR/月、227 人贡献、约每天一个稳定版、6 个月专职环境投入、
  成熟的 CI 与静态分析基建。把这些数字当基准衡量我们自己的产出会得出荒谬结论。
- **数字性质**：全部是**团队自报**，非受控实验；0.5% 是**相对值**。她自己也在演讲里强调
  "这是他们团队的结果，不是排行榜"，二手传播时这句最容易被删掉。
- **"禁 99% 注释"是产品代码库的本地政策**，不能推广成"不要写文档"。她自己划的边界是：
  无法编码的直接判断才用 prose；知识文档的必要性不因此降低。
- **"PR 默认就是好的、大部分不再需要深度 review"是高风险表述**：在有测试和依赖约束的代码库
  成立；在没有这层护栏的流程/配置场景里，同样的自信会直接变成生产事故。
- **二手失真模式（可复用观察）**：把"作者本人/团队"升格成"负责人"；把有机的四层结构压成
  并列清单丢掉顺序；ASR 乱码段落被整段跳过而不是标注；把"不是银弹"的自我限定删掉换成绝对句。
  这四条在这次和上次（11-10 pstack）两条线索里重复出现。

## 10. 当前结论

一手扎实、可全文追溯，是本仓库今年最值得反复读的一篇工程方法论：**它给的是一条判据而不是
一套工具**——能让机器判定的，就不要写在文字里；文字只留给判断。对我们在做的事，最直接的三条：
① 把 Skill/记忆里可脚本化的规则迁到工具层；② 交付标准改成"带验证产物"；③ 验收看回退与返工、
不看工作量。形式化验证和自动合并闭环了解即可，不投入、不照搬。

本卡停留在"学习理解 + 可做小实验"阶段，未改动任何生产配置。
