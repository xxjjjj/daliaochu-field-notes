# 「AI 指挥 AI 四招」：第三次换皮，四招逐条核验

## 1. 这是什么

同一个人、同一批一手材料，被中文短视频第三次改写成新框架。

- Lauren Tan（网名 poteto，自称 Potato），SpaceXSI（xAI）Principal Engineer，做 Grok Bot。
- 一手源只有两个：**Matt Pocock 的 1 小时 5 分对谈**（2026-10-02，就是二创口中"56 分钟访谈"）
  和 **AI Engineer CODE 2026 的 17 分钟演讲**（2026-11-11）。
- 二创已经出现过三版：`2026-11-10` 的"七层心法"、`2026-11-22` 的"3 千 PR"、本条的"四招"。
  三版框架互不相同（七招／四招／无招），说明这是内容生产而不是方法论提炼。

**本条最值得留下的东西不是四招本身，而是它把一个顺序讲反了**：一手原话是"先建信任、再放并行"，
二创把"造总管"排成第一招，读者会先并行、后补验证 —— 正好踩中 Lauren 自己反复警告的坑。

## 3. 先钉住三件事

**① 不是"同一场演讲的两面"，是两个不同材料。**
56 分钟是 Matt Pocock 的直播对谈（10-02），17 分钟是大会演讲（11-11）。内容一脉相承，
但不是同一场。把它们当成"一场演讲的两面"，会让人以为四招出自那个有逐字稿可查的演讲 ——
查下去会发现演讲里根本没有"四招"。

**② "50 多个 AI""干掉 20 多个工程师""马斯克公司九成员工天天在用"，三个数字都没有出处。**
一手能查到的数字是：她个人月发 2,500–3,000 个 PR（她自己强调大量是重构清理，不是 2,500 个功能），
Grok Bot 团队上月 11,000 个 PR、227 人至少交过一个 PR。对谈里她明确说"我不是坐在那里开 2,500 个 chat"，
她的并行单位是 project（她比作一家餐厅），不是 50 个 agent 排班。"九成员工"在对谈与演讲里**零提及**。

**③ 四招的顺序，一手里是反的。**

> "I definitely would not have been able to do this if I had not spent the time thinking about the kitchen,
> the knives and the tools for my agents."（33:32）

她的因果链是：**环境与验证 → 信任 → 才敢并行 → 才有量**。
四招把"造总管"放第一步，等于让人从并行入口进场。她自己对这条路径的说法是：
如果一开始就 spawn 一百个 agent，"你只会得到一堆低质量 PR、回归和 bug"。

## 4. 四招逐条核验

| 二创说法 | 一手对应物 | 判定 |
|---|---|---|
| 第一招：先造总管，它面试你、创建下属、定时巡逻、动态调算力 | Cursor 的 **Projects / coordinator agent**：负责委派、不干自己的活、管理任务清单、spawn 子 agent（38:33–39:28） | 机制真实，**包装失真**。「面试你」「定时巡逻」「动态调算力额度」无一手出处。她还专门说 company brain / context graph 这种说法"不必要地复杂" |
| 第二招：做过一次就封存成技能，扔进私有仓库，换机器换模型贴地址即可接管 | pstack 本身就是这套；`/automate-me` 从本人历史 transcript 里挖纠正、自动起草路由 skill；`Recall` skill 压缩"翻旧对话找上下文"这个动作（1:03:01） | **真实**，且方向比她说的更狠：Lauren 说 skill 正在**变小**——去年的 skill 是"具体命令和实现细节"，现在应该只留 workflow，"skill 会越来越小、越来越紧凑"（1:03:52） |
| 第三招：配独立邮箱和独立账号，把权限和连接器接满，机器之间自己交接 | **outer loop**：bug report 落在 Slack / Linear / X，跟内环不通，人就成了搬 context 的 proxy；接上 Slack MCP 或自家 harness 订阅频道后，agent 自己 triage、自己复现（35:08–37:43） | **内核真实，做法编造**。她的词是 connector / MCP / routines，不是"独立邮箱和账号"。真要落地在企业里，这是账号治理与最小权限问题，不是提示词技巧 |
| 第四招：开口讲两分钟，最后一句话写进规则"先别动手，用你自己的话复述一遍"，复述即验收 | 她的原话是：模型越强，**瓶颈越是你把意图表达清楚的能力**；domain expertise 比以前更重要；所以"grilling"有效——不是让 AI 复述，是**逼你把词抠出来**（6:22–10:13）。对应的 skill 是 pstack 的 interrogate | **半真**。复述属于"对齐"，不属于"验收"。她的验收是 verification：可复跑的命令、真实运行、留痕证据、新鲜 verifier 签字。复述歪了能纠偏，复述对了照样可能做错 |

## 5. 我学到了什么

- **复述验的是"我说明白了吗"，验证验的是"它做对了吗"。** 这是两件事，成本差一个数量级，
  价值也差一个数量级。四招把前者包装成后者，是最容易让人自我感觉良好的失真。
- **"做过就封存"这句话本身带息。** Lauren 自己的最新口径是 skill 要变小、只留 workflow，
  去年那批写满具体命令的 skill 应该被删掉。她的解法不是"加复核日期"，是**让 skill 只存流程、
  把确定性部分沉到 CLI/脚本里**——这样模型换代时脚本不腐、流程不腐，只有措辞会旧。
- **"人不当中转"的真正抓手是外环，不是账号。** 缺的不是 agent 有个邮箱，是所有落到群里/系统里
  的异常信号能自动进到 agent 的输入里。这一层在她那儿叫 outer loop，在我们这儿叫"别让组长当传话筒"。
- **评论区那句"算力近乎无限"的反驳方向对，但打得不够准。** 她本人已经承认边界：可验证性差的领域
  很难做到，one-way door 多的场景（丢数据、不可回退）她不建议照搬。所以关键变量不是算力，
  是**这个领域的产出能不能被自动判对错**。

## 6. 对个人能力有什么价值

- 接到 AI 任务，先写一句"什么证据算完成"，再让它动手。比"先复述"值钱得多。
- 自己训练自己：把每次纠正攒下来，看哪类错反复出现 —— 那是该写成检查的地方，不是该写进提示词的地方。
- 复述可以留，但放在"动手前"而不是"验收时"：让它复述完，我确认口径，再让它跑。

## 7. 对企业 AI 落地有什么价值（泛化口径）

- **顺序不能反。** 业务流程里 agent 要接的是真实客户数据，one-way door 比代码库多得多。
  先在一个流程上把"什么算做对、怎么留证"跑稳，再谈并行。反过来就是更快更贵地制造错误。
- **四招里唯一可以直接搬的是第二招的内核**：每类任务先有一份"何时用/怎么判完成"的流程卡，
  确定性部分写成脚本。这和内部知识库建设是同一件事，不需要给 agent 开账号。
- **第三招在企业里要降级执行**：不是给 agent 独立邮箱，是把信息源接成只读连接器
  （群消息、系统状态、工单），写入类动作保留人工确认。
- **"九成员工都在用"这类话不要往内部传。** 一句无出处的话会把整个方法论的可信度拉低。

## 8. 可做的小实验

- 挑一个高频 agent 任务，补一条验收定义："这个任务做完，我能看到什么证据"（可复跑的命令/截图/记录链接），
  连跑两周，记录返工次数。
- 对比实验：同一任务，A 组只加"先复述"，B 组只加"验收证据要求"，看哪种减少来回次数更多。
- 以上仅为候选，未获明确指令前不动手。

## 9. 风险和边界

- **本条线索本身就是风险样本**：同一人同一素材，三版二创给出三套互不相同的框架和三个不同的数字。
  传播链越长，方法论越像鸡汤。
- **数字不可外传**：2,500/11,000 PR 是代码"园艺"（重构、删模式、清理）为主的量，不等于业务产出。
- **场景不可移植**：她的高信任环境有内建 CI、lint、类型系统、正式验证；业务流程多数没有对等物。
- **第三招在企业内是安全红线**：agent 独立账号、自行注册平台、自管密码，与账号治理冲突。

## 10. 当前结论

四招里：**第二招真实且已开源可查，第三招内核真实但做法编造，第四招半真（对齐≠验收），
第一招机制真实但顺序被讲反了**。三个吸睛数字全部无出处。

真正值得带走的一句是 Lauren 自己的：**"先花时间把厨房、刀和工具磨好，然后你才不用站在厨房里。"**
在这个顺序下，四招只算操作细节；顺序反了，四招就是加速器。
