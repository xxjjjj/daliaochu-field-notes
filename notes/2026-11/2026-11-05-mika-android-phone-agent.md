# Mika：跑在安卓本机的开源 Phone Agent

## 1. 这是什么

Mika 是一个安卓本机 AI 助理（Phone Agent）：用户一句话交代任务，它在一块**看不见的后台虚拟屏**上像人一样看屏、找按钮、点击、输入、滚动，替用户操作手机里任意 App 和内置浏览器，主屏仍可正常使用。2026-10-29 在 GitHub 建仓，Apache-2.0 协议，Kotlin + Jetpack Compose，作者王赞（@wangzan101）。

群内截图是抖音自媒体对该项目的推介视频，标题"将诞生一批百万富翁"属于引流夸张话术，不是事实；视频内嵌的王赞 X 发帖内容与 GitHub README 一致，项目本体真实可查。

热度（各口径数字均标注时间，star 仍在快速变化）：10-30 单日 +713 star（Trendshift）；11-02 约 4,414 star / 840 fork（apiyi 博客引 GitHub API）；11-04 第三方统计约 6,174 star（dvirbi）。属于一周内爆发的新项目，不是成熟项目。

## 3. 核心观点 / 核心能力

1. **后台虚拟屏是核心差异点。** 传统手机自动化（自动点击器、RPA 录制）执行时霸占前台、人不能用手机；Mika 在独立 background display 上跑自动化，前台焦点不受影响（Android 14+ 才有独立焦点，12/13 上后台操作可能干扰主屏）。
2. **不依赖事先适配，靠"看屏"操作。** 技术栈是 Android 无障碍服务（Accessibility）读控件 + 随 APK 自带的端侧 OCR 读自绘界面文字 + 可选多模态模型看图定位按钮，"看得到就能操作"。另有纯文本的 App/网站知识库（core/.../knowledge、skills 目录），社区可补充。
3. **BYOK、无自有服务器。** 支持 OpenAI 兼容、Anthropic、Gemini 等端点和 ChatGPT 登录，请求只发到用户自己配置的模型商，不经 Mika 服务器。主模型必须支持工具调用；另有看图模型、轻量模型两个可选档位。
4. **本机 Linux 沙箱。** PRoot 起 Alpine Linux 3.22 最小根文件系统，每个对话一个工作区，可跑 Python/Node/shell 处理文件，默认断网；仅 arm64 设备。
5. **安全边界设计。** 登录、验证码、付款强制通知用户接管，App 挪到主屏由人操作，付款/密码页 Agent 看不到画面；默认"询问模式"（花钱先问，发消息/提交/删除直接做），可选"自主模式"（官方原话：自主模式下的动作由用户自己负责）。记忆本地加密存储，不记密码验证码。
6. **MCP 设备桥。** 手机经 USB 连电脑后，电脑端 AI 工具可通过 `http://127.0.0.1:8765/mcp`（需令牌、仅数据线、局域网默认关）给 Mika 派任务——手机变成电脑 Agent 的外设。
7. 其余：定时/条件任务、悬浮胶囊双击发屏提问、内置桌面级浏览器（带翻页随机停顿、识别风控拦截页不硬闯）、任务过程可回看（来源、截图、token 用量）。系统要求 Android 11+（聊天/网页/沙箱），App 控制需 12+，推荐 14+；不支持 iOS。

## 4. 我学到了什么

- **Phone Agent 的技术路线正在收敛为"虚拟屏 + 无障碍 + 多模态看屏"。** Mika 不是孤例：zafiro 走 Shizuku（root optional），dsh-go 把 harness 塞进口袋。手机端 Agent 在 2026 年 10 月底出现集中爆发，和桌面端 Agent 框架的分化路径同构——只是把"操控浏览器/IDE"换成"操控任意 App"。
- **"不霸屏"是手机自动化从玩具变工具的临界点。** 后台虚拟屏解决的是人机抢占同一屏幕的根本矛盾，这个机制比"接入了哪个大模型"更值得记住。
- **Mika 的知识库/技能组织方式和 Hermes Skill 同构。** 纯文本、按 App/网站分目录、社区可 PR——说明"给 Agent 喂场景知识"的做法正在成为行业通用范式，不是某一家的设计。
- **作者对风控是有意识的**（浏览器随机停顿、识别风控页、批量操作随机间隔、到上限即停），但这只缓和浏览器侧；App 侧靠 Accessibility 模拟人工，平台风控另有识别手段。

## 5. 它是否可信，哪些需要验证

可信度分层：

- **高可信（一手可查）**：仓库真实存在、Apache-2.0、Kotlin、功能清单、系统要求、BYOK 架构、MCP/沙箱机制——均来自官方 README 和 docs。
- **自述未独立复测**：后台屏不干扰主屏的实际流畅度、看屏操作成功率、微信/小红书等具体 App 的完成率，官方演示视频均为加速播放；README 自己承认"主要在一台安卓 14 手机上测试过"。
- **未核实**：视频字幕称作者为"瞬维AI创始人、前阿里/影刀技术专家"，未经独立信源确认。
- **数字注意时效**：star 数各信源口径差异大（2k→4.4k→6.2k 跨越几天），引用时必须带查询日期。
- 待验证清单：① 真机（备用 Android 14 机）实测安装配对门槛；② 同一任务在询问/自主模式下的 token 成本；③ 微信/小红书对 Accessibility 自动化的风控反应（见第 9 节，这是最大未知数）。

## 6. 对个人能力有什么价值

- 个人低风控场景可以替代一部分手机上的重复劳动：信息汇总（群聊/博主内容总结）、网页比价筛选、定时提醒类任务、手机本地文件处理。
- 它的 MCP 桥提供了一种新拓扑：电脑上的 Agent 调手机能力（收发微信、调用手机专属 App），补桌面 Agent 触达不到的移动端。
- 学习价值：`docs/architecture.md` 按代码现状写了带类名的架构，`:core` 是纯 Kotlin 可在电脑上用假模型跑单测，是研究端侧 Agent 工程结构的可读样本。

## 7. 对企业 AI 落地有什么价值

- **对本组 RPA 运维线是一个品类信号。** 现有 RPA 谱系（来也合作项目、自研影刀、腾讯 WorkBuddy）都在桌面/云端；Mika 代表"手机端个人 RPA"的新形态，后台虚拟屏 + 自然语言指令可能重塑移动端自动化的交付形态，值得在 RPA 平台雷达里单立"Phone Agent"一类跟踪。
- **销售/运营场景的想象空间与红线并存。** BOSS 直聘批量打招呼、小红书博主采集、微信群总结这类需求真实存在，但 Mika 复用的是个人登录态、跑在个人手机上，企业场景下的数据归属、行为审计、离职交接全部无解，不能直接当企业工具推广。
- **可借鉴的架构细节**：高危动作（付款/验证码/密码）强制人机交接的拦截设计、每任务 token 与过程可回看、知识库纯文本社区化——这三条在设计企业内部 Agent 的权限与审计时都可以直接参考。

## 8. 可做的小实验

- 备用 Android 14 机 + 自费模型 key，从 GitHub Releases 装官方 APK（核对 SHA-256 与签名），跑三个无封号风险任务：内置浏览器比价、群聊文本总结、定时任务；记录配对耗时、任务成功率、token 花费。
- 不开任何主号社交平台，只在测试账号上验证 Accessibility 操作的风控反应，观察周期至少两周再决定去留。
- 暂不建议：装入工作机、接入企业微信/工作微信、配置任何企业系统登录态。

## 9. 风险和边界

1. **账号封禁是首要风险，且已有公开预警。** X 评论区第一反应就是"小红书你敢用 accessibility，风控分会砍一节"。Accessibility 服务是各大平台风控的重点识别特征，批量打招呼、批量互动即使带随机间隔也可能触发；这与本组一贯的社交平台自动化封号口径一致——只读、小号、备用机，不动主号。
2. **权限面极大。** 无障碍服务理论上可读屏、可代操一切界面；虽然开源 + BYOK + 无中转压缩了作恶面，但侧载 APK 的供应链风险仍在，只应从官方 Releases 安装并核对签名，二次打包版不可碰。
3. **极早期 beta。** 建仓不足月、版本号 v0.1.x、升级可能不兼容、单机型测试为主，崩溃和行为漂移要预期在内。
4. **自主模式责任自负。** 官方明确付款确认都不拦截的模式下动作由用户负责，企业设备上不应启用。
5. **成本不透明。** 看屏类任务多模态调用频繁，真实花费要实测；视频和报道均未给成本数据。
6. **平台条款风险独立于技术。** 即使 App 不崩，模拟操作本身可能违反微信/小红书/BOSS 等用户协议，封号和限流是平台权利。
7. 仅安卓，iOS 无路线图。

## 10. 当前结论

Mika 是 Phone Agent 赛道目前完成度最高的开源样本之一，"后台虚拟屏解决霸屏"是真创新，架构（BYOK、无中转、高危接管、MCP 桥、本地沙箱）设计克制且可信。但它是一周龄的 beta 项目，且核心使用场景直面平台风控红线。结论：**列入 RPA/Agent 雷达持续跟踪，允许备用机小号做无风险实验，不进工作机、不碰主号、不做企业级承诺。** 抖音"诞生百万富翁"式话术忽略不计。
