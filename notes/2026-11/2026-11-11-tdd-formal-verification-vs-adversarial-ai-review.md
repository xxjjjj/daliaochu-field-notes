# TDD + 形式化验证 vs AI 对抗性互审：观点核验

## 1. 这是什么

一条抖音技术短视频的主张：反对让多个大模型围着静态 diff 做对抗性代码审查，认为这条路假警报多、真故障抓不到，还会逼写代码的 Agent 塞满防御性废代码；真正的正路只有两条——具体功能用 **TDD + 真实运行验证**，复杂架构/并发状态机用 **大模型做形式化验证（TLA+/Kani）**。视频还给了两个衡量工程质量机制的硬指标。

本质是观点输出，不是实证研究：无作者技术背景背书、无自有数据，"十有八九假警报""100% 拦住"均为断言。但选题踩在 2026 年 AI 编码工程化的真争论上，值得用一手材料校准。

## 2. 原始来源

- 发现入口：群内抖音视频文字稿（视频本体未直接观看，结论基于文字稿）
- 追源到的一手/高可信材料：
  - FormaLLM 研究《Can LLMs Write Correct TLA+ Specifications?》（arXiv:2606.05792，2026-06）：25 个开源模型 + 5 个商用模型、2,600+ 次运行
  - TLA-Prover 论文（arXiv:2606.06133）：20B 参数 TLA+ 专用微调模型
  - Claude Agent SDK 形式化验证实践（Boris Cherny，Lean 4 + TLA+，2026）
  - QASecClaw 多 Agent SAST 假阳性过滤研究（arXiv:2605.01885）
  - Datadog 工程博客、CMU SEI 博客：LLM 过滤静态分析告警的生产实践
  - Kani 官方文档与 GitHub（model-checking/kani）、Hillel《What TLA+ can and can't check》

## 3. 视频核心主张（原样提炼）

1. 大模型对抗性审查失灵：模型算不清全局不变量、没把程序真跑起来，只能按字面猜，于是把所有"像风险"的地方全报上来，十有八九假警报。
2. 逆向污染：写码 Agent 为过关，往干净的 10 行核心改动里塞防御性分支和冗余兜底，token 多烧几倍。
3. 真故障（UI 死循环卡死、启动 KeyError、端口未绑定）盯着 diff 的审查模型一个没看出来——因为这些只有跑起来才暴露。
4. 正路一：TDD——先写测试看到真实跑红（FAIL）→ 写刚好跑绿的实现 → 拉起真实程序点一遍，落盘数据和界面渲染实证通过。
5. 正路二：形式化验证——大模型把架构抽成状态机规约，交 TLA+/Kani 穷举所有交错步序（视频举例"36 交错步序"，无出处），先在故意改坏的模型上跑红抓死锁；重复犯两次的错按"从硬到软"焊进工程底座（单一状态源 → 类型系统让非法状态编不过 → TDD/静态检查自动拦 → 最后才写文档）。
6. 两个硬指标：① 真实线上故障回放拦截率（历史故障放回去能不能 100% 拦住）；② 每拦一个真问题的假警报代价。

## 4. 一手核验：视频哪里站得住，哪里过头

### 4.1 站得住的部分

- **TDD 红-绿-真实运行是成熟工程共识**，无新意但正确。"真实运行一次胜过 diff 互审十轮"在 UI 卡死、配置漏配、端口绑定这类故障上确实成立——静态 diff 结构性看不到运行时状态。
- **两个硬指标是好东西**，尤其"故障回放拦截率"本质是突变测试/回归库思路，可直接落地为团队质量门（我们自己的 agent-policy-regression-eval 技能就是同一思路：把真实判例放回去测拦截率）。
- **"从硬到软焊错误"的排序有工程道理**：单一事实源/类型约束（机器强制）> 自动化测试 > 文档（靠人自觉），约束越强越可靠。

### 4.2 过头或失真的部分（带证据）

**勘误 1："大模型非常适合把架构抽成状态机"——当前可靠性其实很低。**
FormaLLM（2026-06，25 个开源模型 2,600 次运行）：最佳提示策略下 TLA+ 规格只有 **26.6% 能通过语法解析，8.6% 能通过 TLC 模型检查**；模型大小都不预测质量，DeepSeek r1:8b 反而胜过 70B 版。结论原话：当前模型没有专家参与无法生成可靠的 TLA+ 规格。TLA-Prover 专门做了个 20B 微调模型来补这个坑，本身就说明通用模型干不好。

**勘误 2：成功的形式化验证案例是"专家+模型"，不是"模型自己做"。**
2026 年 Boris Cherny 用 Opus 5.5 + Lean 4/TLA+ 验证 Claude Agent SDK 状态机：1,529 条定理、零 sorry、发现 24 个 bug（19 个由证明直接发现），是真实有效的标杆案例——但操作者是 Anthropic 的资深工程师，人在回路里写规约、判结果。视频把这层专家门槛隐去了。

**勘误 3：把"对抗性审查"稻草人化了。**
视频批的是无上下文、围着 diff 挑刺的单模型审查，这确实噪声大；但 2025-2026 的证据表明结构化的多 Agent 对抗/过滤机制恰恰是降噪手段，不是噪声来源：
- QASecClaw（arXiv:2605.01885）：SAST 先报候选、LLM 过滤 Agent 带源码上下文逐条裁决，假阳性从 560 降到 64（-88.6%），召回只降 3.1%，F1 从 78.39% 升到 90.93%。
- Datadog、CMU SEI 的生产实践同构：**LLM 不做独立审查者，只做确定性工具（SAST/测试/编译器）告警的过滤层**。
- 对抗模式（reviewer/challenger/arbiter 三角）的设计目的正是压制单模型"为显 thorough 而过度上报"的倾向。
视频把"裸 LLM 互审"和"有确定性工具垫底的混合审查"混为一谈，一棍子打死。

**勘误 4：TLA+ 和 Kani 不是同层工具，视频并列处理会误导选型。**

| | TLA+ | Kani |
|---|---|---|
| 验证对象 | 设计层抽象状态机（独立于实现语言） | Rust 实际代码（作用在编译器 MIR 上） |
| 擅长 | 分布式协议、并发、工作流状态机的设计缺陷 | Rust 的 panic、整数溢出、unsafe 未定义行为、函数契约 |
| 边界 | 证明的是模型不是上线代码，模型与实现之间有 gap（Hillel Wayne/Karate Labs 均强调需要可执行孪生体补） | 仅 Rust 可用；有界模型检查，靠 small-scope hypothesis，不是无限穷举 |

"交给 TLA+ 或 Kani 穷举所有步序"这句话对两者都不准确：TLA+ 穷举的是抽象模型的状态空间，Kani 是有界的符号执行。非 Rust 代码库根本用不了 Kani。

**勘误 5："100% 拦住"是修辞不是数据。** 形式化验证的强度取决于规约覆盖率，规约本身写错（把缺陷写进模型）时 TLC 会安静地通过——Karate Labs 的 fleetquote 案例实测演示了这个陷阱。故障回放拦截率可以向 100% 逼近，但前提是故障库持续积累且规约与代码同步，没有一劳永逸。

## 5. 人话翻译

视频讲的事用大白话：别让几个 AI 对着代码 diff 打嘴仗——它既没运行过程序也看不见内存，只能把"看起来可疑"的全报上来混工作量，逼得写代码的 AI 为了过关往里灌没用的判断分支。靠谱的办法是让机器用确定性方式说话：测试先钉死预期行为、程序真跑起来看结果；并发和状态流转这种人脑推演必漏的死角，把流程写成状态机让模型检查器把所有走法枚举一遍。但视频没说的是：状态机规约现在让 AI 独立写，十次里九次不合格，还得专家把关；而且 TLA+ 查的是图纸，Kani 查的是 Rust 现房，两个工种不一样。

## 6. 对个人/团队工程工作流的转译

与 Crystal 现有"贵模型动脑 + 便宜模型动手 + harness 总线"工作流直接相关的四条：

1. **给执行侧 Agent 的质量门应押在确定性工具上，而不是再加一个审查 Agent。** 便宜模型（DeepSeek 系）动手时强制：先交测试并跑出真实 FAIL → 实现到 GREEN → 真实运行/真实 API 调用留证。这与 Hermes "finishing the job、真实工具输出为准" 的口径一致。
2. **若要引入 AI 审查，定位成"过滤器"不是"检察官"**：先让编译器/linter/测试/SAST 出确定性告警，LLM 只带上下文裁决真假阳性——有 QASecClaw/Datadog 的数据支持这种混合架构。
3. **状态机思路轻量化用，不必上 TLA+。** 本组面对的飞书审批流、公海池状态流转（自建→领取→已签约→回收）、定时任务状态本身就是状态机：先用一页状态表 + 非法流转清单 + 属性测试（Python Hypothesis 类）覆盖，成本远低于 TLA+；真出现并发/多端同步死角再考虑规格语言，且必须有人能审规约。
4. **两个硬指标直接收编**：每个自动化/Agent 技能建一个"历史故障回放库"，改动后回放测拦截率；同时统计假警报率。这比"再雇一个模型互审"可度量得多。

## 7. 可做的小实验

- 实验 A（低成本）：挑一个本组脚本（如公海池/CRM 只读工具），补 3-5 个历史真实故障做成回放测试，量化当前拦截率，建立基线。
- 实验 B：让主模型把一个飞书审批流转写成状态表（ states + 合法 transition + 不变量），人工审一遍后用 Hypothesis 生成随机事件序列找非法流转——体验"模型抽状态机 + 人审 + 机器穷举"的真实成本，对照 FormaLLM 的 8.6% 合格率预期。
- 暂不建议：在当前 Python/TS 为主的代码库引入 TLA+/Kani 正式流程（Kani 仅限 Rust；TLA+ 规约 AI 自主合格率 8.6%，专家门槛高，投入产出比不成立）。

## 8. 风险和边界

- 视频是二手观点素材，所有定量断言（36 步序、100%、十有八九）无一手出处，引用时须与本笔记的核验数据区分。
- 形式化验证不是免费午餐：规约写错会给出虚假安全感；有界检查不覆盖界外；设计模型与上线代码的 gap 需要可执行孪生体或持续对齐机制。
- TDD 在 UI/探索性原型/一次性脚本上成本可能不划算，视频未讨论适用边界。

## 9. 可复用的 Agent 工程指令草案（待决定是否固化为 Skill）

> 你在写代码时遵守以下质量门，不做静态 diff 式自我辩护：
> 1. 任何功能改动先写测试，并实际运行确认 FAIL（附真实输出），禁止无 FAIL 直接写实现。
> 2. 实现以刚好跑绿为准，不加未被测试或需求要求的防御性分支/兜底/深拷贝。
> 3. 跑通测试后拉起真实程序或调用真实接口做端到端验证，留存运行证据（输出、截图、落盘数据）。
> 4. 涉及状态流转/并发的改动，先交状态表（状态清单、合法流转、不变量、非法流转拦截点）再写码。
> 5. 审查意见只接受可复现证据：报错信息、失败用例、类型/静态检查输出；无法复现的"可能风险"不据此改码。
> 6. 同一故障出现第二次，按"单一事实源 → 类型/静态约束 → 自动化测试 → 文档"顺序固化，优先机器强制。

## 10. 当前结论

视频方向感正确（确定性验证 > 嘴皮子互审）、两个硬指标可直接收编，但论证有三处失真：高估了 LLM 自主写形式化规约的可靠性（实测合格率 8.6%）、稻草人化了结构化对抗审查（混合模式假阳性可降 88.6%）、混淆了 TLA+ 与 Kani 的层次。对本组的实际建议：**TDD + 真实运行 + 故障回放库现在就做；形式化验证只取"状态机思维"做轻量化实践，不上重型工具链；AI 审查若引入，限定为确定性工具告警的过滤层。** 价值阶段：待验证（观点已核验，落地实验未做）。
