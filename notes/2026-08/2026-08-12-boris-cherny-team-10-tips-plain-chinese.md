# Claude Code 团队 10 个技巧——Boris 原帖完整说人话翻译版

> **原帖**：Boris Cherny（Claude Code 创建者），2026-01-31
> https://x.com/bcherny/status/2017742741636321619
>
> **先说结论**：这不是一套必须照抄的标准答案。Boris 的原话意思是：团队每个人的用法都不同，先多试，留下真正适合自己工作环境的方式。

## 1. 一次别只干一件事：并行跑起来

团队认为，最明显的效率提升来自于：**同时开 3～5 个独立工作目录，每个目录跑一个 Claude Code 会话。**

比如：

- A 目录让 Claude 改一个功能；
- B 目录让 Claude 补测试；
- C 目录让 Claude 查一个线上问题或分析日志；
- 你不用等 A 做完，才开始 B。

团队多数人用 `git worktree` 管理这些独立目录；Boris 自己更习惯直接 clone/checkout 多份代码。重点不在于必须选 worktree，重点是：**不同任务不要挤在同一个代码目录和同一段上下文里。**

为了少切换，有人把几个 worktree 起短名字，再配 shell 别名（例如 `za`、`zb`、`zc`），按一下就能跳过去。还有人专门留一个“分析目录”，只查日志、跑 BigQuery，不在里面改代码。

**你可以怎么用：**

- 先别贪多，两个并行任务就够：一个改功能，一个补测试/做验证；
- 每个目录只做一件事，完成后测试、提交、合并，再同步其他目录；
- 复杂且强耦合的事情不要硬并行，否则会把等待 AI 变成你自己来回切脑子的负担。

原帖：https://x.com/bcherny/status/2017742743125299476

## 2. 复杂任务别上来就写：先把方案聊清楚

碰到多文件改造、新功能、重构这类复杂工作，先让 Claude 进入 **Plan Mode（规划模式）**。把“要怎么做、改哪里、怎么验证、有什么风险”聊透以后，再让它动手。

Boris 团队的做法是：**计划做得越清楚，后面越可能一次做对。**

有个人的用法更进一步：

1. 先开一个 Claude 写实施计划；
2. 再开第二个 Claude，要求它按“资深工程师”标准审这份计划；
3. 计划过关后，才开始改代码。

如果执行中发现方向不对，别逼它在错路上缝缝补补。**立即切回规划模式，按现在已经发现的新信息重新规划。**

甚至连“怎么验证”也值得先规划，不只是“怎么开发”。

**你可以直接这样说：**

> 先不要改代码。阅读相关模块后，给我一份可执行的实施计划：涉及哪些文件、每步改什么、风险是什么、怎么验证。等我确认再开始。

原帖：https://x.com/bcherny/status/2017742745365057733

## 3. 把每次纠错变成下次不用再说的规则：经营 CLAUDE.md

`CLAUDE.md` 可以理解为：**这个项目里，给 Claude 的长期工作说明书。**

当你发现 Claude 又犯了一个重复错误，不要只说“这里错了，改掉”。改完后再补一句：

> 把这条补进 CLAUDE.md，确保下次不要再犯同样的错。

Boris 的意思是：Claude 很擅长把人给它的纠正，整理成以后能遵守的规则。

但这个文件不是越长越好。要不断删改，把过时、重复、没用的规则清掉，直到你能明显感觉到同类错误变少。

团队里有人让 Claude 为每个项目/任务维护一个 `notes` 目录：每做完一个 PR 就把关键决定、踩坑和验证结果写进去；然后在 `CLAUDE.md` 里告诉 Claude，遇到相关任务去读对应 notes。

**适合写进 CLAUDE.md 的内容：**

- 项目特有的命令：怎么启动、测什么、构建什么；
- 团队明确的代码规范和禁忌；
- 经常踩到的坑及规避方法；
- 提 PR 前必须完成的检查；
- 安全或数据边界。

**不适合：**教科书常识、过长的背景介绍、一次性临时要求。它们会占上下文，反而干扰判断。

原帖：https://x.com/bcherny/status/2017742747067945390

## 4. 重复两次以上的事，不要一直手搓：封成 Skill 或命令

团队经验是：**一天里要做不止一次的操作，就值得封装。**

可以做成 Claude Code 的 Skill / slash command，提交到 Git，让项目组其他人也复用。这样不需要每一次都重新打长提示词，也不会每个人都发明一套做法。

原帖给了几个例子：

- `/techdebt`：每次会话结束前跑一下，专门找重复代码、顺手清掉技术债；
- 一个“上下文打包”命令：把最近 7 天 Slack、Google Drive、Asana、GitHub 的相关信息汇总给 Claude，减少人工找背景；
- 做一个数据分析工程师型 Agent：负责写 dbt 模型、审代码、在开发环境验证改动。

**说人话**：如果你经常在重复“整理信息 → 让 AI 分析 → 输出固定格式结果”，就不要每次临时描述，直接把步骤、输入、输出、检查规则固化下来。

原帖：https://x.com/bcherny/status/2017742748984742078

## 5. Bug 不要自己先排半天：把证据给 Claude，让它闭环

团队的思路不是“把修复步骤拆开，一步步指挥 AI”，而是：**把它定位和验证需要的证据给够，然后让它自己查、自己修、自己验证。**

他们的例子：

- 接好 Slack MCP 后，把 Slack 里的 Bug 讨论串直接贴给 Claude，只说一句 `fix`；
- CI 挂了，直接说：`Go fix the failing CI tests`（去修失败的 CI 测试）；
- 分布式系统出问题，就把 Docker 日志给它，让它去定位。

这里不是说不需要人参与，而是不要在没必要时微操每一个步骤。

**前提很关键：**给的材料必须足够让一个工程师定位问题——复现方式、期望结果、实际结果、报错日志、截图、关联链接、可运行的验证命令。最后仍要以测试、日志或页面实际效果验收，不能只相信它说“已经修好”。

原帖：https://x.com/bcherny/status/2017742750473720121

## 6. 别只把 Claude 当执行员：让它反过来审你

Boris 给了三种提问方式。

### 6.1 让它当审核人，反过来考你

可以说：

> 针对这些改动来考我。在我通过你的检查前，不要创建 PR。

或者：

> 证明这个方案能跑通。请比较 main 分支和当前 feature 分支的实际行为差异。

这会让 Claude 从“照做的人”变成“找漏洞的人”。

### 6.2 方案一般，就推倒重来

如果第一版只是“能跑”但不够好，不要在它上面不断加补丁。可以说：

> 基于你现在掌握的全部信息，推翻刚才的方案，重新给出一个更干净、更合理的实现。

### 6.3 需求越具体，返工越少

把工作交给 Claude 前，尽量把规格写清楚：要解决什么、不能动什么、验收标准是什么、要跑哪些测试。少一点模糊表达，输出就会好很多。

**一句话总结**：不要接受第一版；要求它自证、反思、重做，通常它能比第一版更好。

原帖：https://x.com/bcherny/status/2017742752566632544

## 7. 把终端当作多任务工作台，而不是黑框

团队里很多人喜欢 Ghostty 终端，因为它在多会话场景下，画面刷新、颜色和字符显示都不错。

但不是让大家必须换 Ghostty。真正值得学的是它的工作台思路：

- 用 `/statusline` 自定义状态栏，常驻显示当前上下文用量、所在 Git 分支；
- 多个终端标签页按任务/工作目录命名、上色；
- 可以配合 tmux，一个任务或一个 worktree 一个 tab；
- 一眼就知道哪个 AI 在忙、哪个任务在哪个分支、哪个上下文快满了。

另一个建议是用系统语音输入。Boris 的观察是：人说话通常比打字快 3 倍，而且说出来时会自然补足背景，prompt 更完整。macOS 上连按两次 `fn` 可以启动听写。

原帖：https://x.com/bcherny/status/2017742753971769626

## 8. 用子代理分工：主会话管方向，子会话干脏活

子代理适合做能独立完成的子任务，比如查代码结构、找调用链、查测试缺口、整理日志、做方案对比。

原帖给了三种做法：

1. 想让 Claude 在一个问题上投入更多并行计算，就在请求中明确写 `use subagents`；
2. 把局部任务交给子代理，主会话只保留目标、关键决策和最终整合，避免上下文被大量中间过程塞满；
3. 用 Hook 把权限请求交给 Opus 4.5 做安全扫描：风险低的自动通过，有攻击/注入风险的拦住。

**边界：**

- 子代理不是越多越好。子任务边界不清，会重复查、结论互相矛盾、成本也更高；
- 自动批准权限只能放行最小范围、确定安全的操作；涉及删除、外发、生产环境、敏感数据仍要人工确认。

原帖：https://x.com/bcherny/status/2017742755737555434

## 9. 数据分析别只靠手写 SQL：把数据工具接给 Claude

Claude Code 团队把 BigQuery 的 `bq` CLI 和一个 BigQuery Skill 接进了代码库。团队成员可以直接让 Claude 取数、写查询、分析指标，不需要每个人都自己手写 SQL。

Boris 说他个人已经 6 个多月没手写过 SQL。

这个办法不局限于 BigQuery：只要一个数据系统有 **CLI、MCP 或 API**，理论上都可以接进来，让 Agent 帮你做查询和分析。

**前提不是“把数据库交给 AI 随便查”**，而是要先有：

- 清楚的账号与最小权限；
- 可审计的查询日志；
- 脱敏和数据导出边界；
- 关键结论能复核的指标口径；
- 生产数据不能被随意写入或外发。

原帖：https://x.com/bcherny/status/2017742757666902374

## 10. Claude 不只是写代码工具，也可以当老师

原帖给了四个学习用法：

1. 在 `/config` 里打开 `Explanatory` 或 `Learning` 输出风格，让它改代码时同时解释：为什么这样改；
2. 让它把陌生代码整理成一个可视化 HTML 小演示，用图和页面讲清楚模块关系；
3. 让它用 ASCII 图画协议、架构、调用流程，先快速搭起全局理解；
4. 做一个间隔重复学习 Skill：你先讲自己怎么理解，它不断追问暴露盲区，最后把结果存下来，下次再复习。

**说人话**：别只让它直接给答案。让它用你听得懂的方式解释、追问、出题、复盘，才真的能把能力留下来。

原帖：https://x.com/bcherny/status/2017742759218794768

## 视频里哪些不是这篇原帖的内容

为了避免二手内容混在一起，单独说明：

- `/allowed-tools`、`/terminal-setup`、`/theme`、`/install-github-app` 这些命令都是真实能力，但**不是这篇 2026-01-31 原帖的 10 条内容**。其中原帖第 7 条只明确提到 `/statusline`、终端 tab 管理和 macOS 语音输入。
- 视频提到的三种流程（例如 `explore → plan → confirm → code → commit`）**出自 GitHub Copilot CLI 的官方最佳实践，不是 Boris 这篇 Claude Code 团队帖的内容。**
- 视频提到国内账号限制，也是视频作者的现实观察，并非 Boris 原帖的内容。

## 最值得直接照做的三件事

1. **复杂任务先计划、确认后执行**：少返工；
2. **每次纠错都沉淀成规则**：同类错误不再反复发生；
3. **给 AI 明确的验证路径**：测试、日志、页面检查齐全，不能只听它说“做完了”。
